# 数据库设计

> 当前 main 收口注记（2026-09-02）：V001～V019 均纳入版本化迁移序列；V001～V018 为既有基线/渐进迁移，V019 增加库存释放结果去重、过期预占重试字段及 `CHECK_REQUIRED`/`RELEASE_FAILED` 终态约束。当前运行边界是四个独立服务、三个有状态 service DB；`life_assistant`、`business_state`、单体 profile 和回滚脚本继续保留为兼容能力。

> 正文中若出现“DemoStore 当前承接全部业务”或“未来再拆服务”，均指历史迁移阶段；当前表归属只以 [`architecture/data-ownership.md`](architecture/data-ownership.md) 为准。

## 1. 持久化方案

> 四服务目标 Schema、唯一写入者、跨服务副本和禁止项见
> [`16_三服务接口数据归属与契约草案.md`](./16_三服务接口数据归属与契约草案.md#5-数据和-schema-归属)。
> 本页同时记录 legacy/单体关系表和已落地的服务表；当前独立数据归属、Outbox/Inbox/Saga 以 D07 和架构矩阵为准。

数据库基线确定为 MySQL 8.4、InnoDB、`utf8mb4`。金额统一以“分”为单位存入 `BIGINT UNSIGNED`，Java 枚举以 `VARCHAR` 原名保存，时间精度为毫秒。`DemoStore` 继续承接现有领域规则，但全部可变业务状态由 `BusinessStateRepository` 保存；Compose/Kubernetes 选择 JDBC 适配器，将状态拆解到 V001 关系表并从关系行重建领域状态，本地直接运行默认保留文件适配器，不改变 REST 契约。

版本迁移位于 `database/migrations/VNNN__description.sql`。`database/bin/migrate.sh` 按版本顺序执行文件，在 `schema_migration` 中记录版本、描述、SHA-256 和应用时间。已应用文件被修改时会因 checksum 不一致失败，禁止静默篡改历史迁移；后续变更必须新增更高版本文件。

Compose 在空数据卷首次启动时通过 `database/init/10-bootstrap.sh` 按版本顺序应用 V001～V019 并登记 checksum；演示数据位于 `database/seeds/demo-data.sql`，仍只由显式 `db-seed` 命令载入。脚本可重复执行，并保留演示基线依赖的商家 ID `1..4`、商品 ID `1001..1007` 和演示账号。密码仅保存 Spring Security 兼容的 BCrypt hash；演示弱密码不得用于生产环境。

## 2. 数据字典

| 表 | 主键/关键字段 | 约束与用途 |
|---|---|---|
| `schema_migration` | `version`、`checksum`、`installed_at` | 记录不可变版本迁移，不属于业务数据 |
| `business_state` | `state_key`、`payload`、`updated_at` | V003 旧版兼容表；启动时若发现活动快照则一次性导入关系表，稳态保持为空 |
| `category` | `id`、`name`、`icon` | 分类名唯一，软删除 |
| `merchant` | `id`、`category_id`、`avg_score`、`status` | 关联分类；按分类/状态和评分/销量索引 |
| `user_account` | `id`、`phone`、`password_hash`、`role`、`merchant_id` | 手机号唯一；角色限制为三种现有 Java 枚举值 |
| `user_address` | `id`、`user_id`、`is_default` | 关联用户；“最多 5 个地址/单默认地址”由事务内业务规则保证 |
| `auth_session` | `id`、`user_id`、`token_hash`、`expires_at` | 只存 token 摘要，支持过期与撤销；供后续认证迁移 |
| `product` | `id`、`merchant_id`、`price_cent`、`stock`、`version` | 库存非负；`version` 预留乐观锁；按商家和上架状态索引 |
| `group_deal` | `id`、`merchant_id`、`price_cent`、`stock`、`version` | 团购库存及启停状态 |
| `cart_item` | `id`、`user_id`、`product_id`、`quantity` | `(user_id, product_id)` 唯一；数量限制 `1..99` |
| `order_main` | `id`、`user_id`、`merchant_id`、`order_type`、`status`、`total_cent` | 保存商家名和地址快照；按用户、商家/状态查询；`version` 预留并发控制 |
| `order_item` | `id`、`order_id`、`item_type`、`item_id` | 保存名称、单价快照；多态商品 ID 不设外键 |
| `order_status_timeline` | `id`、`order_id`、`status`、`occurred_at` | 同一订单同一状态唯一 |
| `payment_record` | `id`、`user_id`、`order_id`、`client_request_id`、`status` | V002 后 `(user_id, client_request_id)` 唯一并记录 order_id；同 key 跨订单返回 409；状态含 `PROCESSING/SUCCESS/FAILED` |
| `coupon` | `id`、`order_id`、`merchant_id`、`code`、`status` | 一单一券、券码唯一；按商家/状态核销查询 |
| `review` | `id`、`order_id`、`user_id`、`merchant_id`、评分 | 一单一评；三项评分限制 `1..5` |
| `merchant_favorite` | `(user_id, merchant_id)` | 用户与商家的复合主键收藏关系 |
| `chat_message` | `id`、`user_id`、`merchant_id`、`sender_role` | 按会话和发送时间索引 |
| `operation_log` | `id`、`actor`、`action`、`created_at` | 按时间及操作人查询的审计记录 |
| `merchant_catalog` | `id`、`merchant_id`、价格、库存、上架状态 | V004；merchant-service 渐进切流期间的服务自有商品表 |
| `order_record` | `id`、`user_id`、`merchant_id`、商品、金额、状态 | V004；order-service 渐进切流期间的服务自有订单表 |

所有业务外键均使用 InnoDB 约束。订单项中的 `item_id` 有意不直接外键到商品或团购表，因为它是多态引用，订单展示依赖快照字段，不应因商品后续修改而变化。

## 3. 数据生命周期

准备 `.env` 后运行：

```bash
docker compose up -d --wait mysql
docker compose --profile db-tools run --rm db-migrate
```

空数据卷会自动完成基线 Schema 初始化。仅在本地演示或测试需要数据库样例数据时，再显式运行 `docker compose --profile db-tools run --rm db-seed`。

- 重复迁移：已应用且 checksum 一致时安全跳过。
- 重复 seed：通过主键/唯一键 upsert 恢复基准数据，不产生重复行。
- 清理业务数据：`docker compose --profile db-tools run --rm db-clean`；保留表结构和迁移历史。
- 空库重建：`docker compose down -v` 后重新执行上述初始化流程。
- 生产环境：只执行 `db-migrate`，禁止执行 `db-seed` 或 `db-clean`。

`db-seed` 和 `db-clean` 的底层脚本分别要求 `ALLOW_DEMO_SEED=true` 和 `ALLOW_DATABASE_CLEAN=true`。Compose 工具服务会在显式调用时传入对应开关，直接运行脚本时若未授权会拒绝执行。

## 4. 配置与安全

Compose 不再提供数据库密码默认值，`MYSQL_ROOT_PASSWORD`、`MYSQL_USER`、`MYSQL_PASSWORD` 必须通过未提交的 `.env` 或部署环境注入。`.env.example` 仅包含占位值。脚本通过 `MYSQL_PWD` 向客户端传递密码，避免密码出现在命令行参数中。

数据库账号建议遵循最小权限：应用账号仅拥有目标 Schema 的 DML 权限；迁移账号拥有目标 Schema 的 DDL 权限；生产环境不向应用或迁移任务暴露 root 密码。当前 Compose 为本地开发简化为同一非 root 数据库账号，生产部署时应拆分。

## 5. 验证与后续边界

CI 使用 MySQL 8.4 实际执行“两次迁移、两次 seed、校验、清理、重新 seed、再次校验”，覆盖 V001～V019 的迁移序列、历史兼容表、服务表、关键索引、固定 ID、行数与重复执行。后端单元测试额外验证 seed 中 BCrypt hash 可由 Spring Security 匹配；Compose 测试通过 API 写入购物车，直接断言 `cart_item` 关系行和空的 `business_state`，随后重启后端并再次通过 API 验证恢复。

Compose/Kubernetes 已通过 `JdbcBusinessStateRepository` 接入 MySQL 关系表。一次保存会在同一事务和 MySQL 命名写锁内同步账号、目录、购物车、订单、支付、券码、评价、会话、收藏及日志，异常时整体回滚；读取则由关系行重建领域聚合。当前领域聚合仍是单写者模型，因此 Kubernetes 后端在此阶段固定为一个副本。后续拆成独立服务时，应进一步改为各 Service 按请求操作其自有表并补充库存竞争等并发测试。
