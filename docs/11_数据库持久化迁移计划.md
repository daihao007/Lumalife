# 数据库持久化迁移计划

## 当前结论

当前代码已经从 Controller 直接调用 `DemoStore` 调整为 Controller 调用业务 Service 门面，再由 Service 委托内存版 `DemoStore`。这为数据库迁移留下了清晰替换点：后续可以逐个 Service 从内存实现替换为 Mapper/Repository 实现，而不需要改动前端接口契约。

本阶段不建议一次性把全部内存数据迁移到数据库。原因是订单、支付、库存、券码、评价和评分更新存在事务关系，如果同时迁移所有模块，容易破坏当前已经可演示的主链路。

## 迁移目标

- 保持现有 `/api/v1/**` 接口路径、请求体和响应体不变。
- 保持现有自动化测试继续通过；数据库资产落地后的本分支基线为 48 个。
- 新增数据库集成测试，覆盖登录、下单、支付、商家履约、评价、团购核销。
- 数据库金额字段继续使用分，类型使用 `BIGINT`。
- 状态字段继续使用枚举名称，数据库使用 `VARCHAR` 保存。

## 推荐技术路径

Schema 生命周期已经确定为 `database/migrations/VNNN__description.sql` 版本文件和 `schema_migration` checksum 历史表；演示 seed 与生产迁移分离，详见 `docs/06_数据库设计.md`。业务代码接入数据库时优先使用 Spring JDBC 或 MyBatis-Plus，避免在课程演示项目中过早引入复杂 ORM 关系映射。

建议新增依赖：

- `spring-boot-starter-jdbc`
- `mysql-connector-j`
- 如选择 MyBatis-Plus，再增加 `mybatis-plus-spring-boot3-starter`

建议新增配置：

- `application-dev.yml`：本地 MySQL 配置。
- `application-test.yml`：测试可使用 H2 或 Testcontainers MySQL。
- 复用现有版本迁移工具执行建表，不再使用启动期 `spring.sql.init` 自动载入演示 seed。

## 表迁移顺序

1. 基础字典与账号
   - `user_account`
   - `user_address`
   - `category`
   - `merchant`

2. 商品与团购
   - `product`
   - `group_deal`

3. 购物车
   - `cart_item`

4. 订单主链路
   - `order_main`
   - `order_item`
   - `order_status_timeline`
   - `payment_record`

5. 团购券码
   - `coupon`

6. 评价与评分
   - `review`
   - 评价提交后重算或增量更新 `merchant.avg_score`

7. 管理与观测
   - `operation_log`

## Service 替换顺序

1. `AuthService`
   - 先迁移用户登录、注册、当前用户和地址。
   - 验证：登录成功、密码错误、普通用户 `merchantId` 为空、地址最多 5 个。

2. `CatalogService`
   - 迁移分类、商家搜索、详情、商品和团购公开查询。
   - 验证：关键字搜索、分类过滤、推荐排序、详情返回商品/团购/评价。

3. `CartService`
   - 迁移购物车。
   - 验证：加购、改数量、删除、清空、下架商品不可加购。

4. `OrderWorkflowService`
   - 迁移外卖下单、团购下单、支付、取消、用户订单、评价。
   - 验证：支付幂等、库存扣减、状态机、重复评价限制。

5. `MerchantAdminService`
   - 迁移商家后台商品维护、订单履约、团购维护、券码核销。
   - 验证：跨商家越权返回 403/业务拒绝，非法状态流转返回 409。

6. `AdminDashboardService` 和 `AssistantService`
   - 管理员指标改为数据库聚合。
   - AI 客服仍可保持规则型实现。

## 回滚策略

- 每迁移一个 Service，只替换该 Service 的底层实现，其他 Service 继续委托 `DemoStore`。
- 保留 `DemoStore` 到迁移完成，作为演示回退实现。
- 使用 Spring Profile 区分：
  - `demo-memory`：内存演示版。
  - `dev-db`：数据库开发版。
- 如果某个模块迁移后测试失败，可以切回 `demo-memory` 继续演示。

## 验证清单

每完成一个 Service 迁移后必须运行：

```bash
cd backend
mvn test
```

数据库版额外手工验收：

- 重启后演示账号仍可登录。
- 重启后商品、订单、评价、券码仍存在。
- 支付重复提交不会重复扣库存。
- 商家管理员不能处理其他商家的订单。
- 管理员看板数据与订单数据一致。

## 下一步建议

下一次实际编码应从 `AuthService` 数据库化开始，范围控制为用户、Token、地址三块；不要同时迁移订单和支付。
