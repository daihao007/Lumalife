# 数据库持久化迁移记录与后续计划

## 当前结论

生产与容器环境已不再把 MySQL 仅用于 Schema 生命周期验证。Controller 继续调用业务 Service 门面，领域规则由 `DemoStore` 承接，可变状态通过 `BusinessStateRepository` 持久化；当 `LUMALIFE_PERSISTENCE=mysql` 时，`JdbcBusinessStateRepository` 将领域状态映射到 V001 的规范化关系表，并从这些表恢复。

V003 的 `business_state` 表不再是稳态数据源。升级已有环境时，如发现 `state_key=primary` 的旧 JSON 快照，应用会在首次读取时事务性导入关系表，成功后删除该活动快照。该兼容表暂时保留，避免直接升级造成数据丢失。

## 已完成范围

| 业务区域 | 稳态关系表 | 已验证行为 |
|---|---|---|
| 账号与地址 | `user_account`、`user_address`、`merchant` | 登录、注册、资料、地址和商家账号恢复 |
| 目录 | `category`、`merchant`、`product`、`group_deal` | 搜索数据、商品/套餐维护、库存和上下架恢复 |
| 购物车 | `cart_item` | 加购、改数量、删除、清空及重启恢复 |
| 订单与支付 | `order_main`、`order_item`、`order_status_timeline`、`payment_record` | 拆单、状态时间线、支付请求号和库存结果恢复 |
| 券码与评价 | `coupon`、`review` | 团购券状态、评价事实和评分数据恢复 |
| 收藏、客服与审计 | `merchant_favorite`、`chat_message`、`operation_log` | 收藏关系、跨角色会话和操作日志恢复 |

保存过程在一个数据库事务内执行，并使用 MySQL 命名锁保证单写者同步；任一关系表写入失败会整体回滚。数据库清理工具同时清理旧 `business_state`，避免清库后意外恢复旧数据。

## 配置与回滚

- 本地直接启动默认 `LUMALIFE_PERSISTENCE=file`，便于无 MySQL 的开发和单元测试。
- Docker Compose 与 Kubernetes 固定设置 `LUMALIFE_PERSISTENCE=mysql`，MySQL 是这些环境的业务持久化依赖。
- 如需紧急回退，可切换到文件适配器；切换前必须明确文件状态与数据库状态的取舍，不能双写。
- 现阶段领域聚合仍常驻单进程，Kubernetes 后端保持单副本，避免不同实例使用不同内存版本覆盖数据库。

## 自动化验收

后端规则与接口测试：

```bash
cd backend
mvn test
```

CI 的 Compose 验收还会：

1. 在空 MySQL 上启动后端并用演示账号登录；
2. 通过真实 HTTP API 加入购物车；
3. 直接查询 `cart_item`，确认关系行已写入；
4. 确认 `business_state` 稳态行数为零；
5. 重启后端并重新登录，确认购物车仍能从关系表恢复。

## 后续架构演进

本次已经完成“业务落入 MySQL 关系表”，但尚未完成微服务化或多副本并发模型。后续应在不改变 `/api/v1/**` 契约的前提下：

1. 将整个领域状态同步进一步拆成 `IdentityRepository`、`CatalogRepository`、`OrderRepository` 等按请求读写接口；
2. 把库存扣减、支付幂等、券码核销和评价提交改成更小的事务边界，并补充并发竞争测试；
3. 将登录令牌从进程内状态迁移到 `auth_session` 或独立认证服务；
4. 完成上述工作后再允许后端水平扩容和三服务独立写入。
