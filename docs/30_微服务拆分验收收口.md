# 微服务拆分验收收口

本文把课程评分中“至少三个业务微服务、数据归属清晰、跨服务通过接口调用”的要求落到当前代码基线。附件评分细则是验收标准；本文件是仓库内的实现索引，并明确区分已实现的四服务切分与库存预占仍处于兼容窗口的部分。

## 1. 已完成的核心拆分

| 服务 | 业务边界 | 生产数据库 | 对外依赖 |
| --- | --- | --- | --- |
| `identity-service` | 登录、注册、用户资料、头像 URL、地址、会话 | `life_assistant_identity` | 仅保留 `merchantId` 不透明引用 |
| `merchant-service` | 商家、分类、商品、团购、库存预占、收藏、商家会话 | `life_assistant_merchant` | 仅保留 `userId`、`orderId` 不透明引用 |
| `order-service` | 购物车、订单、订单明细、支付幂等、履约、券码、评价、状态事件、订单 Outbox | `life_assistant_order` | 通过 HTTP 调用 merchant 的商品/库存边界 |
| `assistant-service` | 平台客服、商家客服答案、Agnes provider 和 deterministic fallback | 无业务库 | 接收 BFF 提供的脱敏商家上下文 |

`backend` 是兼容 BFF，浏览器继续访问 `/api/v1/**`；切流打开后，身份、商家目录和订单域分别通过内部 HTTP 契约转发到三个服务。内部接口统一使用服务令牌，并对用户/商家写操作校验身份头。

## 2. 数据归属门禁

机器可读的归属表在 [`services/data-ownership.yml`](../services/data-ownership.yml)。三服务代码只允许访问自己数据库中的表：

- identity 负责 `user_account`、`user_address`、`auth_session`。
 - merchant 负责 `category`、`merchant`、`merchant_catalog`、`group_deal`、收藏、会话、库存预占表、`merchant_inbox_event` 和 `merchant_outbox_event`。
 - order 负责 `order_record`、订单明细/状态事件、购物车、支付、券码、评价、`service_outbox_event`、`order_inbox_event` 和 `order_inventory_saga`。
- assistant 无业务表，AI 请求是无状态内部契约。

旧的 `life_assistant` 只用于迁移、回填、单体兼容和回滚；服务运行时使用独立数据库名。`scripts/test-service-data-ownership.sh` 会扫描服务源码中的 SQL，并在发现跨域表访问时使 CI 失败；同时校验 Compose/Kubernetes 的数据库接线。

## 3. 跨服务一致性边界

配送下单由 BFF 读取 identity 地址快照和 merchant 商品快照后调用 order；order 只保存订单自己的金额、商品名称和地址快照。支付时 order 通过 merchant 的库存预占接口建立 reservation；支付成功后在同一订单事务写入库存确认 Outbox，由 RabbitMQ 投递给 merchant，merchant 在 Inbox 幂等记录后确认库存，再通过 merchant Outbox 回传结果，order Inbox 更新 Saga 状态。支付事务失败时，释放命令在新事务中写入 Outbox，避免补偿随着原事务回滚。

这是评分细则要求的“通过接口调用并处理失败”加可靠事件投递实现。订单状态和库存确认/释放命令在 order-service 本地事务内写入 Outbox，由 RabbitMQ 传递；merchant 的 Inbox 和 order 的 Inbox 都以唯一事件 ID 去重。库存预占尚未完全改为异步命令，因此当前应准确描述为“事件驱动确认/补偿 + 同步预占兼容窗口”，而不是假称支付入口已经完全异步化。

### 3.1 远程指标投影

当 order 远程切流和回填开关同时打开时，`RemoteMetricsServicePort` 会通过内部 HTTP 调用：

- identity-service 的 `/internal/v1/admin/accounts`，取得不含密码和 token 的账号摘要；
- merchant-service 的 `/internal/v1/merchants`，取得商家名称和基础评分；
- order-service 的 `/internal/v1/orders/metrics`，取得订单状态、营收趋势、履约时效、活跃订单和订单侧排行。

backend 只负责组合这些只读投影，不再从 `DemoStore` 读取远程模式下的指标源数据。该聚合仍是 BFF 查询编排，不应描述为独立 metrics 服务或事件驱动投影。

### 3.2 运行时 Outbox、RabbitMQ 和 Inbox

订单创建、取消、支付、履约、收货、券码和评价状态变更，在 order-service 的本地事务中同时写入 `service_order_event` 与 `service_outbox_event`。启用 `LUMALIFE_EVENTS_BROKER_ENABLED=true` 后，order 和 merchant 两侧的 Outbox publisher 按固定间隔发布待处理/失败事件并在 broker 接受后标记 `PUBLISHED`；merchant-service 通过 `merchant_inbox_event`，order-service 通过 `order_inbox_event` 做 at-least-once 消费去重，Saga 状态保存在 `order_inventory_saga`。旧的 HTTP publisher 仍可用于迁移期回退，但生产清单默认使用 RabbitMQ。

### 3.3 AI 客服服务化

`assistant-service` 是无状态可独立部署服务，暴露 `POST /internal/v1/assistant/answer`。backend 的 `AssistantService` 只拼接商家资料和会话历史，通过 `AssistantAnswerPort` 调用该服务；Agnes provider、超时处理和 deterministic fallback 均位于 assistant-service。单体回退时才启用 backend 的 `LocalAssistantAnswerPort`，远程切流时 `DemoStore` 和本地 AI adapter 都不会创建。

### 3.4 物理数据库隔离

默认 Compose/Kubernetes 仍保留旧的单实例逻辑数据库模式以兼容课程数据和回滚；服务运行时只连接各自的逻辑数据库，跨域 SQL 门禁禁止把旧库当作可写事实源。`docker-compose.physical-db.yml` 提供 `mysql-identity`、`mysql-merchant`、`mysql-order` 三个独立实例，服务通过 `MYSQL_IDENTITY_HOST`、`MYSQL_MERCHANT_HOST`、`MYSQL_ORDER_HOST` 连接；`database/bin/isolate-service-databases.sh` 从已回填的兼容库按表所有权导出数据。该 overlay 是可回滚的物理隔离路径，不会覆盖现有 `mysql_data`。

## 4. 验收命令

```bash
bash scripts/test-service-data-ownership.sh
mvn -B -ntp -f services/pom.xml verify
docker compose up --detach --build --wait
docker compose --profile db-tools run --rm db-seed
docker compose --profile db-tools run --rm db-backfill-services
```

CI 中的 `service-data-ownership`、四服务构建、Compose stack smoke、API/UI 回归和 K8s rollout 共同构成拆分验收证据。性能对比和 HPA 实际观测不属于本次拆分 PR 的完成条件，避免用未执行的实验结果代替事实。
