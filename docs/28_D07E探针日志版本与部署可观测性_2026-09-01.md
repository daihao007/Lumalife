# D07E 探针、日志、版本与部署可观测性实施记录

## 1. 验收范围

本记录对应 Issue #50，覆盖 `identity-service`、`merchant-service`、`order-service`，并补齐网关
backend 的关联 ID 传播以及 frontend 的部署版本查询。

| 工作负载 | 活性 | 就绪 | 版本 |
| --- | --- | --- | --- |
| backend | `/actuator/health/liveness` | `/actuator/health/readiness` | `/actuator/info` |
| identity-service | `/actuator/health/liveness` | `/actuator/health/readiness`，包含状态文件检查 | `/actuator/info` |
| merchant-service | `/actuator/health/liveness` | `/actuator/health/readiness`，prod 包含 DB | `/actuator/info` |
| order-service | `/actuator/health/liveness` | `/actuator/health/readiness`，prod 包含 DB | `/actuator/info` |
| frontend | `/healthz` | `/healthz` | `/version.json` |

Spring Boot 原生 availability health groups 是探针唯一实现。order-service 原先将整体 health 伪装成
liveness/readiness 的 Controller 已删除，避免数据库故障触发错误的进程重启。

## 2. 结构化日志与关联 ID

四个 Java HTTP 入口统一执行以下规则：

1. 接受匹配 `[A-Za-z0-9._:-]{1,128}` 的 `X-Request-Id`，非法或缺失时生成 UUID；
2. 接受 W3C `traceparent`，缺失时生成新的 trace/span；
3. 在响应中回写 `X-Request-Id`；
4. backend 的所有 `RestClient` 请求传播 `X-Request-Id`、`traceparent` 和 `X-Caller-Service`；
5. stdout 每行输出一个 JSON 对象，不记录 Authorization、token、密码、请求体或个人信息；
6. 请求完成事件包含 service、version、requestId、traceId、method、path、status、durationMs。

测试运行中得到的日志结构示例：

```json
{"message":"HTTP request completed","service":"order-service","version":"dev","requestId":"d07-order-001","traceId":"1aca9d3ddd8646039926fea0548922e8","event":"http_request_completed","method":"GET","path":"/actuator/health/readiness","status":200,"durationMs":4}
```

## 3. 版本一致性

流水线统一使用：

- 镜像 tag、运行时 `SERVICE_VERSION`、Kubernetes `app.kubernetes.io/version`：`sha-<7 位>`；
- `GIT_COMMIT`、OCI `org.opencontainers.image.revision`：完整 Git SHA；
- Java `/actuator/info`：service name、version、contract-version、git.commit；
- frontend `/version.json`：service、version、gitCommit。

`scripts/deploy-k8s.sh` 在一次渲染中替换五张镜像、版本标签、运行时版本和 Git SHA；如果仍存在
`:main`、`version: main` 或 `value: unknown`，部署立即失败。

## 4. 部署失败定位记录

### 4.1 已发生故障

历史 CI [运行 #171](https://github.com/daihao007/Lumalife/actions/runs/33402493336) 的
`Kubernetes rollout smoke test` 失败，backend Pod 进入 `CrashLoopBackOff`，随后发布 Job 被阻断。

定位过程如下：

1. `kubectl get deployments,pods -o wide` 确认 backend 未 Ready 且持续重启；
2. `kubectl describe pods` 排除调度和镜像拉取问题；
3. `kubectl logs` 与 `kubectl logs --previous` 显示 backend 启动时无法从 MySQL 关系表加载业务状态；
4. `kubectl get events --sort-by=.lastTimestamp` 将失败时间与 rollout 对齐；
5. 根因为应用版本所需关系表/数据尚未在旧 PVC 上完成迁移和回填，而应用已经开始启动；
6. 修复为部署时先执行版本化迁移和幂等 backfill，再等待应用 rollout；失败时自动输出当前/previous
   日志、describe、events 和 rollout history；
7. 后续主线运行 #179/#183 的 Kubernetes smoke/deploy 成功，证明迁移顺序修复后可以恢复发布。

### 4.2 可复现演练

`scripts/test-deployment-observability-k8s.sh` 只允许在 `kind-*` context 运行。脚本给
identity-service 注入一个不存在的镜像 tag，要求 rollout 按预期失败，从 Pod/Event 中识别
`ErrImagePull`、`ImagePullBackOff` 或 pull failure，保存诊断证据，然后执行 rollout undo，并断言恢复到
原镜像且 Deployment Ready。

GitHub Actions 的 `Kubernetes rollout smoke test` 会执行该演练，并始终上传
`d07-deployment-failure-evidence` artifact，其中包含场景、失败 rollout、workload 状态、Deployment/Pod
describe、Events、rollout history 和恢复结果。

## 5. 自检

```bash
mvn -f backend/pom.xml test
mvn -f services/pom.xml test
bash scripts/test-deploy-k8s.sh
kubectl kustomize k8s
```

带固定 ID 验证关联链路：

```bash
curl -H 'X-Request-Id: d07-check-001' http://localhost:8080/api/v1/categories
docker compose logs backend identity-service merchant-service order-service \
  | jq -R 'fromjson? | select(.requestId == "d07-check-001")'
```

最终流水线还必须通过五个工作负载 rollout、四个 Java 服务 liveness/readiness/info、frontend
health/version，以及隔离 Kind 部署失败和恢复演练。
