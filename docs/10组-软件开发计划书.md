## 1 引言

### 1.1 编写目的

本文规定 LumaLife 综合生活助手平台的开发范围、过程、组织、进度、质量、配置、风险和交付安排，为五名项目成员、课程指导教师及后续接力者提供统一执行基线。本文是对历史计划书的当前实现校准，不反向补造已经缺失的站会、截图或实际工时记录。

### 1.2 系统概述

LumaLife 是面向课程实践的本地生活服务 Web 系统，覆盖 9 个业务场景：用户身份与地址、商家发现与收藏、跨商家购物车和拆单、订单履约与评价、团购购买与券码、商家核销、商品与套餐维护、用户/商家/AI 客服、平台运营看板。

当前默认运行链路为：

```text
frontend -> backend BFF/API facade -> identity-service
                                 -> merchant-service
                                 -> order-service
                                 -> assistant-service

order-service <-> merchant-service via RabbitMQ Outbox/Inbox/Saga
```

默认 Compose 共 8 个服务，包括 6 个应用服务、MySQL 和 RabbitMQ。系统保留 `monolith` profile 作为迁移基线、性能对照和回滚手段，但它不是当前默认业务运行模式。

## 4 工作范围与约束

### 4.1 功能范围

正式需求范围固定为 `REQ01~REQ09`，不在最终验收阶段随意新增业务。剩余开发只能用于阻断缺陷修复、测试补齐、证据闭环、文档校准和答辩准备。

### 4.2 技术约束

- 后端：Java、Spring Boot、Maven；声明兼容 Java 17。
- 前端：React 18、TypeScript、Vite、npm。
- 数据：MySQL；服务数据库为 identity、merchant、order 三个逻辑/物理归属。
- 消息：RabbitMQ Outbox/Inbox/Saga；不得把 timeout 或 503 描述成 circuit breaker。
- 部署：Docker Compose 和 Kubernetes/K3s；镜像使用不可变 `sha-*` 版本。
- 支付：仅模拟支付，不连接真实资金渠道。
- AI：未配置 `AGNES_API_KEY` 时使用确定性降级回复。

### 4.3 进度与资源约束

课程集中实践按 D01～D10 组织，共 5 名成员、50 个计划任务。每项计划 7 小时，合计 350 计划工时。该数字仅用于容量规划；实际投入尚无完整成员原件，不在本文估算或代填。

### 4.4 安全与合规约束

- 账号密码使用 BCrypt 哈希保存，演示弱密码只允许出现在明确的本地 seed 环境。
- 公共接口实施角色鉴权和输入校验，敏感配置通过环境变量或 Secret 注入。
- 禁止将真实凭据、个人隐私、服务器连接信息写入仓库和答辩材料。
- AI 使用、开源依赖和证据来源须如实说明。

## 5 开发过程与方法

### 5.1 过程模型

采用“迭代增量 + 每日任务 + 阶段门禁”的过程：

1. 建立需求和单体基线；
2. 完成三层设计与追溯；
3. 按业务域拆分微服务和数据归属；
4. 补齐单元、API、集成和 E2E；
5. 建立容器、CI/CD 与 Kubernetes；
6. 执行 HPA、故障和性能实验；
7. 统一文档、答辩材料与最终审计。

每次迭代以范围明确的小提交结束，提交前执行相关测试或将未执行项显式标为 `NOT-RUN`。

### 5.2 需求与设计方法

- 使用结构化用例描述参与者、前置条件、基本流程、扩展流程和后置条件。
- 统一使用 `REQxx / UCxx / SYS-SEQxx / COMP-SEQxx / OBJ-SEQxx` 作为目标编号。
- 服务边界按身份、商家目录、交易履约、AI 助手划分。
- 跨服务数据通过 HTTP 契约、事件和快照传递，不使用跨库联表。
- 重大架构与可靠性取舍记录在正式设计文档和当前事实源中。

### 5.3 实现与代码标准

- Java 使用 4 空格，TypeScript 使用 2 空格；遵循仓库既有格式。
- 公共 API 统一位于 `/api/v1`，内部服务契约位于 `/internal/v1`。
- 控制器只负责输入/输出和鉴权边界，业务逻辑位于服务层或独立微服务。
- 数据库变更使用版本化迁移；已应用迁移必须校验哈希，不得静默改写。
- 缺陷修复遵循“复现—隔离—最小修复—回归—记录”。

### 5.4 可复用产品

项目使用 Spring Boot、Spring Security、Jackson、React、Vite、Vitest、Playwright、Recharts、MySQL、RabbitMQ、Docker 和 Kubernetes 等成熟组件。版本由 Maven `pom.xml`、npm lockfile、Dockerfile 和工作流配置锁定；不得继续沿用历史计划中的 Vue、Element Plus、Redis 或 MyBatis-Plus 口径。

仓库内部复用能力包括统一 API 响应、错误映射、请求 ID、远程服务端口、订单状态线、测试辅助、数据库迁移和部署守卫。

### 6.3 实现与集成顺序

1. identity-service：认证、用户、地址、会话和账号查询；
2. merchant-service：商家、目录、收藏、客服和库存投影；
3. order-service：购物车、订单、支付、券码、评价和 Saga；
4. assistant-service：AI provider 调用和降级回复；
5. backend BFF：对外 API、角色鉴权、服务编排和错误映射；
6. frontend：角色路由与三类工作台；
7. Compose/CI/Kubernetes：构建、集成、镜像和部署门禁。

集成时优先验证契约和数据归属，再验证端到端业务流。order 与 merchant 的库存链路使用消息 Saga；失败状态和人工核验边界必须保留。

### 6.4 测试活动

当前源码定义 221 个正式测试 case：108 个 Unit/Component、94 个 Integration/API、19 个 E2E。另有 6 个 Shell 验证套件，不并入 case 数。

| 层级 | 主要目标 | 准入条件 |
|---|---|---|
| Unit/Component | 服务逻辑、前端组件、路由和交互 | 有断言，正常/边界/异常至少覆盖相关风险 |
| Integration/API | Spring 上下文、鉴权、52 个公共 API、服务契约 | 状态码、响应体、权限和关键副作用均有断言 |
| E2E | 9 个微服务业务场景、3 个 UI 核心流、7 个 legacy API 场景 | 绑定提交、隔离环境和原始 artifact |
| Shell/Static | 数据归属、迁移、RabbitMQ、K8s、部署脚本 | 不修改共享业务数据；危险套件仅在可销毁环境执行 |

现有证据不是同一当前提交的全量重跑：本地逐套结果和旧提交远程证据必须保持分层。恢复 E2E 时只能使用本地隔离、可销毁环境，不得用服务器旧提交冒充当前结果。

### 6.5 CI/CD 与发布

CI 质量门按变更检测、后端/服务测试、前端测试与构建、API/E2E/静态守卫、镜像构建发布、Kubernetes smoke、部署和健康验证串联；上游失败必须阻断下游。镜像发布使用 `sha-<commit>`，不得只使用 `latest` 或可漂移标签。

最终发布前需要：

1. 拉取并确认目标 `main`；
2. 运行与改动风险匹配的本地验证；
3. 确认 CI 绑定当前提交；
4. 审核镜像版本与清单；
5. 保存 smoke、部署与健康证据；
6. 创建课程提交标签或 Release，并附交付清单。

### 6.6 配置管理

- 所有源代码、脚本、清单、Markdown、模型源和正式 PDF 纳入 Git。
- `main` 是共享稳定分支；多人并行时使用 `codex/*` 或功能分支并通过评审合并。
- 接力直推 `main` 时必须先 `pull --ff-only`，使用范围清晰的小提交，禁止 force push。
- `monolith-start` 标签保存改造前基线；当前交付使用提交哈希标识。
- 用户原有未跟踪文件不得擅自删除、覆盖或纳入提交。

### 6.7 问题与变更管理

问题通过 GitHub Issue、PR、提交和最终审计清单跟踪。每个问题至少包含范围、影响、证据、负责人、验收条件和状态。阻断项优先级为 P0，答辩质量缺口为 P1，非阻断优化为 P2。

## 12 质量保证与支持条件

### 12.1 质量门

- 需求：用例字段完整，需求—设计—代码—测试可追溯。
- 代码：相关模块构建通过，关键分支有断言，禁止无关重构混入缺陷修复。
- 数据：迁移可重复，服务表唯一归属，危险数据操作只在可销毁环境执行。
- 部署：Compose/Kustomize 可解析，探针和不可变镜像策略明确。
- 文档：数字与 `project-facts.md` 一致，无 TODO/占位符、旧架构冒充和内部路径泄露。
- PDF/PPTX：可编辑源存在，最终导出逐页检查，无裁切、重叠、乱码和空白页。

### 12.2 评审与独立性

关键代码和文档应由非直接作者复核；测试执行者应尽量与功能作者分离。自动化审计可以发现问题和生成材料，但不能替代教师确认、成员贡献确认和签字。

### 12.3 需方支持

课程指导方需要提供最终任务书、提交格式、答辩时间、验收反馈和最终用例确认。项目组需要保留这些确认原件；当前教师/助教对最终用例清单的确认仍为 `UNVERIFIED`。
