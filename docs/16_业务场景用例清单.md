# LumaLife 业务场景（用例）清单

> 文档状态：第一版（基于当前单体实现校准的验收基线）
> 最近修订：2026-08-26
> 适用范围：当前演示环境；后续微服务拆分不得改变本清单定义的业务结果

## 编写原则

业务场景（用例）是由一类用户或外部系统触发，为完成一个明确业务目标，从开始到产生可验证结果的一段完整流程。一个用例可以包含主成功流程、备选流程和异常流程，这些是同一用例的不同路径。

单个页面、按钮、接口、数据库操作或流程中的一步，不单独作为用例；登录、注册、查询、收藏、购物车增删改、商品上下架等操作，只有在支撑完整业务目标时才写入对应用例。

本清单中的每个用例均写清参与者、触发条件、前置条件、主成功流程、备选或异常流程、可验证结果，并通过编号对应到需求、设计、代码和测试。最终汇报建议至少选择 `UC03`、`UC04`、`UC05/UC06` 三组详细展示追溯关系。

## 编号规则

本版统一使用以下编号，编号只表达一个维度，避免把核心需求、业务用例和测试层级混为一谈：

| 编号类型 | 格式 | 用途 | 规则 |
| --- | --- | --- | --- |
| 业务需求 | `REQ01`~`REQ09` | 业务目标级需求 | 与正式业务用例 `UC01`~`UC09` 一一对应；原 `CR-01`~`CR-06` 作为历史核心范围保留，不再作为本清单的业务需求编号。 |
| 业务用例 | `UC01`~`UC09` | 用户完成一个完整业务目标的场景 | 页面、按钮、单个接口和单个状态变化不单独编号为用例。 |
| 测试用例 | `TC-UCxx-nn` | 验证某一业务用例的自动化或手工测试 | `xx` 对应用例编号，`nn` 在该用例内从 `01` 顺序编号；Java 测试方法名和手工步骤是测试实现定位。 |

## 当前业务规则口径

- 购物车允许存在多个商家的商品；提交外卖订单时，系统按商家拆分为多个独立订单，并分别计算金额、扣减库存和推进状态。
- `/api/v1/assistant/ask` 提供无需登录的通用规则问答；用户与指定商家的会话、订单上下文咨询和商家回复必须登录并接受数据归属校验。
- 接口成功时 HTTP 状态为 `200` 且响应体 `code=200`；参数错误、未认证、无权限、资源不存在和业务冲突分别使用 HTTP `400/401/403/404/409`，失败时不得产生部分写入或非法状态变化。
- 支付以 `clientRequestId` 作为幂等键；相同请求重复提交必须返回同一业务结果，且库存、券码和交易统计只更新一次。

## UC01 用户建立可消费的账号资料

| 项目 | 内容 |
| --- | --- |
| 对应关系 | `REQ01`；实现与测试证据见“追溯矩阵” |
| 参与者 | 游客、普通用户 |
| 触发条件 | 游客首次使用平台，或已有用户准备执行下单、收藏、客服等需登录操作 |
| 前置条件 | 系统可访问；注册账号未冲突，或已有演示账号可用 |
| 主成功流程 | 1. 游客进入登录/注册页。<br>2. 新用户提交手机号、密码、昵称并完成注册；已有用户提交账号和密码登录。<br>3. 系统校验身份并返回 Token 与用户资料。<br>4. 用户进入个人中心维护昵称、头像和联系方式。<br>5. 用户新增或编辑收货地址，并设置默认地址。<br>6. 系统保存资料，后续购物车结算和外卖下单可读取默认地址。 |
| 备选或异常流程 | A1. 登录密码错误或账号不存在：系统拒绝登录并提示原因。<br>A2. 注册手机号重复或信息不完整：系统拒绝注册。<br>A3. Token 缺失或失效：系统拒绝访问个人中心、订单、购物车等受保护资源。<br>A4. 地址联系人、手机号或详细地址为空：系统拒绝保存。<br>A5. 普通用户访问商家或管理员入口：系统返回无权限提示。 |
| 可验证结果 | 注册成功后账号角色为 `USER` 且密码不以明文保存；登录成功返回非空 Token，并可通过 `GET /api/v1/auth/me` 取得同一用户；资料和默认地址重新查询后与提交值一致；重复注册返回 HTTP `409`，无 Token 返回 `401`，角色越权返回 `403`，失败请求不得改变原数据。 |
| 相关代码模块 | `AuthService`、`SecurityConfig`、`DemoStore`、`ApiControllers`、`Login`、`Profile` |
| 相关接口 | `POST /api/v1/auth/login`、`POST /api/v1/auth/register`、`GET /api/v1/auth/me`、`POST /api/v1/user/profile`、`GET /api/v1/user/addresses`、`POST /api/v1/user/addresses` |
| 测试建议 | 单元测试覆盖账号校验、角色判断、地址字段校验；接口测试覆盖登录、注册、鉴权和地址维护；E2E 测试覆盖注册/登录到建立默认地址。 |

## UC03 用户提交外卖订单并得到支付或取消结果

| 项目 | 内容 |
| --- | --- |
| 对应关系 | `REQ03`；实现与测试证据见“追溯矩阵” |
| 参与者 | 普通用户 |
| 触发条件 | 用户决定购买一个或多个商家的外卖商品 |
| 前置条件 | 用户已登录并有可用收货地址；购物车中的目标商品在售且库存充足 |
| 主成功流程 | 1. 用户在一个或多个商家详情页选择商品加入购物车。<br>2. 用户进入购物车调整数量、删除商品或清空后重新加购。<br>3. 系统按商家分组商品，并分别重新计算订单金额。<br>4. 用户选择收货地址并提交外卖订单。<br>5. 系统逐组校验库存、价格、地址和商品状态，每个商家生成一个待支付订单。<br>6. 用户对目标订单发起模拟支付，系统根据 `clientRequestId` 做幂等处理。<br>7. 支付成功后订单进入已支付或待商家处理状态，并展示订单时间线。 |
| 备选或异常流程 | A1. 购物车为空：系统返回 HTTP `409`，且不创建订单。<br>A2. 购物车包含多个商家：系统按商家拆分订单；任一分组校验失败时不得生成部分订单。<br>A3. 商品库存不足、已下架或价格变化：系统返回业务冲突，订单和库存保持不变。<br>A4. 用户缺少收货地址：系统返回业务冲突并提示先维护地址。<br>A5. 用户取消待支付订单：订单变为 `CANCELLED`。<br>A6. 用户以相同 `clientRequestId` 重复支付同一订单：返回同一订单结果，不重复扣减库存或累计交易额。<br>A7. 用户尝试取消已支付订单：系统返回 HTTP `409`，订单状态保持不变。 |
| 可验证结果 | 若购物车涉及 N 个商家，则一次提交返回 N 个待支付订单且每单仅含一个商家商品；订单金额等于对应商品快照金额之和；地址以订单快照保存；支付成功后目标订单状态为 `PAID`，库存仅扣减一次；待支付订单可取消，已支付订单取消失败且状态不变。 |
| 相关代码模块 | `CartService`、`OrderWorkflowService`、`AuthService`、`DemoStore`、`Detail`、`Cart`、`Orders` |
| 相关接口 | `GET /api/v1/cart/detail`、`POST /api/v1/cart/items`、`POST /api/v1/orders/delivery`、`POST /api/v1/payments`、`POST /api/v1/orders/{id}/cancel`、`GET /api/v1/orders` |
| 测试建议 | 单元测试覆盖购物车修改、跨商家拆单、地址快照、库存不足、支付幂等和取消规则；接口测试覆盖加购、下单、支付、取消及失败时无部分写入；E2E 测试覆盖完整外卖下单闭环。 |

## UC04 商家履约外卖订单，用户确认并评价

| 项目 | 内容 |
| --- | --- |
| 对应关系 | `REQ04`；实现与测试证据见“追溯矩阵” |
| 参与者 | 商家管理员、普通用户 |
| 触发条件 | 用户已支付外卖订单，商家需要履约，用户需要确认消费结果 |
| 前置条件 | 商家管理员已登录并绑定商家；订单归属于该商家且处于可处理状态 |
| 主成功流程 | 1. 商家管理员进入订单管理或商家工作台。<br>2. 系统展示本店待处理订单。<br>3. 商家按规则推进订单状态，例如接单、配送中、完成。<br>4. 用户在订单页查看状态和时间线。<br>5. 用户确认收货或订单达到可评价状态。<br>6. 用户提交评分、口味评分、服务评分和评价内容。<br>7. 系统保存评价并更新商家评分统计。 |
| 备选或异常流程 | A1. 商家处理非本店订单：系统拒绝越权操作。<br>A2. 商家执行非法状态流转：系统返回业务冲突。<br>A3. 已取消订单被履约：系统拒绝。<br>A4. 用户评价未完成订单：系统拒绝。<br>A5. 用户重复评价同一订单：系统拒绝。<br>A6. 评分超出范围或评价内容为空：系统拒绝保存。 |
| 可验证结果 | 商家履约按 `PAID → ACCEPTED → DELIVERING → COMPLETED` 推进；用户可将 `DELIVERING` 或 `COMPLETED` 订单确认为 `RECEIVED`，每次变化均形成时间线；非法流转、跨商家处理和处理已取消订单返回 `403` 或 `409` 且状态不变；仅 `COMPLETED` 或 `RECEIVED` 订单可评价一次；空内容或越界评分返回 `400`；成功评价后订单标记为已评价，商家评分和评价列表同步更新。 |
| 相关代码模块 | `MerchantAdminService`、`OrderWorkflowService`、`DemoStore`、`MerchantOrders`、`MerchantDesk`、`Orders` |
| 相关接口 | `GET /api/v1/merchant-admin/orders`、`POST /api/v1/merchant-admin/orders/{id}/transition`、`POST /api/v1/orders/{id}/receive`、`POST /api/v1/reviews` |
| 测试建议 | 单元测试覆盖订单状态机、越权处理和重复评价；接口测试覆盖商家订单列表、状态流转、确认收货和评价提交；E2E 测试覆盖商家履约到用户评价。 |

## UC06 商家核销团购券并处理异常券码

| 项目 | 内容 |
| --- | --- |
| 对应关系 | `REQ06`；实现与测试证据见“追溯矩阵” |
| 参与者 | 商家管理员 |
| 触发条件 | 用户到店消费并出示团购券码 |
| 前置条件 | 商家管理员已登录；券码来自已支付团购订单；券码对应商家与当前商家一致 |

## 通用验收要求

- 每个用例至少覆盖主成功流程、一个备选流程和一个异常流程。
- 所有支付相关流程必须验证 `clientRequestId` 幂等。
- 跨商家购物车提交时必须按商家拆单；任一分组校验失败时不得生成部分订单。
- 待支付订单允许用户取消，已支付订单不允许用户直接取消。
- 商家只能处理自己店铺的订单、商品、套餐、券码和客服会话。
- 游客可浏览公开内容并使用通用 AI 规则问答，但不能执行收藏、加购、下单、评价或商家客服会话等需登录操作。
- 平台管理员看板只能由平台管理员访问。
- 所有失败请求都必须验证响应状态、错误信息以及核心数据未发生非法变化。
- 单体环境和后续微服务环境都应保留 UC01～UC09 的代表性回归记录。

## 重点展示建议

1. `UC03`：用户从跨商家购物车拆单、支付、取消异常到订单时间线，覆盖用户端、订单状态、库存和支付幂等。
2. `UC04`：商家履约、用户确认和评价，覆盖商家端、状态机、评价和评分统计。
3. `UC05 + UC06`：用户购买团购券、商家核销和异常券码处理，覆盖团购交易、券码状态和越权校验。
