## 1. 启动结论

第二阶段从“方案和骨架”进入“可验证的渐进迁移”。本阶段的最终判断标准不是服务数量，而是每个业务事实是否有唯一所有者、每条切流是否有回填证据、每个失败路径是否可解释和回滚、每个结论是否能从 Issue → PR → 测试 → 文档追溯。

当前已具备：

- `identity-service`、`merchant-service`、`order-service`、`assistant-service` 四个独立 Spring Boot 入口、构建入口和健康探针；
- backend 的身份、商家、订单端口及远程适配器；
- merchant/order 的部分独立 API 和 MySQL 表；
- Compose、Kubernetes、CI 镜像和部署链路；
- `/internal/migration/status` 与远程开关、回滚闸门。

当前不得宣称已完成：

- 所有四服务业务事实已经完全脱离 `DemoStore`；`DemoStore` 仍是显式 monolith/compatibility 回退；
- 支付、库存、券码和评价的所有深层故障场景都已经由跨服务事务、Outbox/Inbox 或 Saga 完整证明；
- HPA 已经完成真实 `metrics.k8s.io`、1→2→3 和冷却→1 观测；多节点、metrics-server 故障和滚动发布联合场景仍未覆盖；
- 所有外部 `/api/v1/**` 仍由 backend 兼容入口承接；当前内部服务为四个，外部目标契约与 64 个源码业务 mapping 不混算；
- PR #117 的历史回归问题已经解决，最终 CI/Kubernetes/ECS 结果以统一 evidence 中的当前 main 链接为准。

### D07 文档交付索引

## 6. 跨服务调用和一致性门禁

### 6.1 同步调用

- 读取类调用必须有明确超时预算；连接失败最多重试一次，不能无限重试。
- 库存预占、释放和支付命令必须携带稳定幂等键；响应超时先查询原操作状态，不能盲目创建第二个操作。
- 请求必须传播 `X-Request-Id`、`traceparent`、`X-Caller-Service`；命令额外传播 `Idempotency-Key`。
- 依赖不可用时不创建可支付半订单；错误响应使用稳定 `reason`，不泄露堆栈、SQL、主机名或密钥。

### 6.2 数据和事件

- 每张业务事实表只有一个服务写入；跨服务只传稳定 ID、不可变快照、版本化 API 或事件。
- order 不直接扣 merchant 的 `product.stock`；库存必须通过 merchant 的 reservation 能力或明确的补偿流程。
- order 的支付、订单状态时间线和 Outbox 必须在本地事务内形成一致结果；消费者先 Inbox 去重再更新投影。
- 事件至少一次投递，必须能处理重复、乱序和未知版本；失败进入可重试或死信路径。
- 在私有 Schema 未形成前，计划只能标记为“共享数据库上的服务表隔离实验”，不能写成“独立数据库完成”。

## 10. 分支与 PR 流程

1. 本计划使用分支 `codex/d06-phase2-service-plan`，不直接写入 `main`。
2. 计划文档先提交本 PR；通过 Markdown、链接和事实一致性检查后，再由至少一名协作者评审。
3. 业务代码按 #43～#58 拆分独立分支和 PR；每个 PR 只覆盖一个清晰门禁，并在描述中链接 Issue、测试和回滚证据。
4. PR 未合并前，Projects 可以标记为进行中，但不能填写“已完成”或把未合并 SHA 当作最终证据。
5. 合并后重新读取 `main` 的 SHA，更新追溯表、报告和部署版本；若 CI、部署或回归失败，保留失败记录并回到对应门禁。
