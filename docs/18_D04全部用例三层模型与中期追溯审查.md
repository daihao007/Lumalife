## 1. 交付结论

本次补齐了 UC04～UC09 的系统级（SYS）、组件级（COMP）和对象级（OBJ）图源，并把九个正式业务用例统一放入同一条追溯链：

`REQ → UC → SYS → COMP → OBJ → 页面/API/Service/领域对象 → TC/HTTP E2E/手工证据`

UC01～UC03 的三层模型沿用 [D03-A 前半用例三层模型与追溯矩阵](17_D03前半用例三层模型与追溯矩阵.md)；本交付补齐 UC04～UC09。当前结论不是“九个用例所有路径均已自动化”，而是：

- 九个正式用例均有业务定义、需求映射、组件级设计和对象级设计。
- 九个正式用例均能定位到当前代码、接口或页面；代码落点以当前单体 Spring Boot + React/Vite + `DemoStore` 为准。
- UC04～UC07、UC09 有后端/API 和中期页面证据；UC09 的健康值是指标接口中的演示字段；UC08 有服务/API 证据，但完整用户—商家会话闭环仍是中期缺口。
- 当前没有 P0 阻断；P1 缺口集中在真实浏览器自动化、客服闭环证据、商家内容维护的页面级负向回归和部分异常路径留证。

### 4.2 中期缺口与处置建议

| 优先级 | 缺口 | 影响 | 后续验收动作 |
|---|---|---|---|
| P1 | 尚无 Playwright/Cypress 级 UI E2E；HTTP 黑盒 E2E 只覆盖 CR-04～CR-06 | 真实浏览器刷新、跨页状态和兼容性不能持续回归 | 保留稳定 Hash 路由和选择器；后续增加 UC01～UC09 代表路径 UI E2E |
| P1 | UC08 用户—商家会话完整闭环没有独立跨角色证据 | 客服主成功流程仍不能在中期审查中单独复现 | 固定用户/商家账号，记录发送、读取、回复、再读取及跨商家 403/400 |
| P1 | UC07 的页面级维护发布链和下架不可购链没有一组完整留证 | API 已覆盖，但不能证明页面交互和用户端刷新一致 | 记录商品/团购新增、编辑、toggle、用户端详情刷新与历史订单快照 |
| P1 | UC04/UC06 的页面级异常提示证据不足 | 后端 403/409 已有测试，但用户是否看懂错误未闭环 | 采集非法状态、重复核销、跨商家核销的页面截图或自动化断言 |
| P1 | UC09 页面未接入真实 Actuator 健康链路，`/admin/metrics` 中的 `health.status` 当前固定为 `UP` | 现有截图只能证明演示指标显示 UP，不能证明实时健康或健康异常 | 当前文档按演示字段描述；若需要真实健康能力，再接入 Actuator 并补成功/异常测试 |
| P2 | `MerchantDesk.tsx` 与正式四个商家页面存在 legacy 重复实现 | 文档、演示和维护入口可能产生歧义 | 继续以 `MerchantOrders`、`MerchantProducts`、`MerchantSupport`、`MerchantShop` 为正式入口，明确 legacy 或移除 |
| P2 | 文档中历史测试快照与当前测试数量并存 | 审查人员可能误把中间快照当作当前基线 | 新增证据以本次命令输出为准，旧记录保留“历史快照”标识并逐步归档 |
| P2 | 当前后端仍为 `DemoStore` 内存实现 | 重启持久化、并发和事务边界与生产实现不同 | 微服务/数据库迁移前保留 UC01～UC09 契约和回归矩阵，禁止以未来架构替代当前证据 |
