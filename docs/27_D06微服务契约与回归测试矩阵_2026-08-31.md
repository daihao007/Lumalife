## 1. 使用口径

- **38 个接口**：identity-service 9 个、merchant-service 12 个、order-service 17 个。`/actuator/health`、`liveness`、`readiness` 属于运维探针，另见第 4 节，不计入业务接口总数。
- **调用边界**：这些接口供 `backend`（BFF）或受信服务调用；浏览器只调用 `backend` 的 `/api/v1/**`，不能把 `/internal/v1/**` 当作前端公网 API。
- **共同鉴权**：每个内部接口都需要 `X-Luma-Service-Token`。表中只额外列出接口特有的 `Authorization`、`X-User-Id` 或 `X-Merchant-Id`；无额外请求头时标为“仅服务令牌”。
- **测试结果口径**：`已有覆盖（本次复验通过）` 仅代表仓库已有测试覆盖了该契约的一部分；`待新增` 表示还没有端到端验证该接口的专门测试，不能写成“通过”。因此“服务测试通过”不等于 38 个接口都已获得完整契约覆盖。

## 2. 测试数据隔离规则

| 编号 | 适用范围 | 隔离规则 |
| --- | --- | --- |
| ISO-ID | identity-service | 每个测试类使用独立临时状态文件或独立测试数据库；注册手机号使用 `ct-id-<runId>` 标识，测试结束删除临时文件，不依赖演示用户。 |
| ISO-MER-R | merchant-service 只读接口 | 只读检查允许读取固定种子商家，但必须断言种子版本；不得依赖测试顺序或前一条写入的数据。 |
| ISO-MER-W | merchant-service 写接口 | 用 `CT-<runId>-商品/套餐` 创建专属数据；在 `finally` 删除或用临时数据源回收，不能污染用户可见商家目录。 |
| ISO-ORD | order-service | 每次使用唯一 `clientRequestId=ct-<runId>-<case>`，并采用全新订单/购物车状态或临时数据库；不复用固定订单号，不把支付测试数据写入共享演示库。支付幂等键的作用域是全局 `(userId, clientRequestId)`，不得为另一订单重用。 |
| ISO-X | 跨服务回归 | 每轮运行生成 `runId`、独立用户和商家；失败时保留该轮原始日志与数据快照，成功后清理临时数据。 |

## 6. 本轮完成定义与后续实施顺序

本文件先完成“**接口完整盘点、UC 映射、契约断言、失败场景和数据隔离规则**”。要达到 Issue #44 的最终验收，还需按以下顺序落地自动化：

1. 为所有标记“待新增”的 `CT-RT-*` 编写 provider 集成测试，优先处理写接口和权限失败场景。
2. 在 BFF 编写 consumer/适配器测试，确认内部服务响应能转换为既有 `/api/v1/**` 前端契约。
3. 以 `CT-RT-X-01~06` 建立 Compose 环境下的跨服务 API E2E，并保存命令、时间、退出码、总数、通过数、失败数和原始日志。
4. 将服务测试、OpenAPI lint 和跨服务 E2E 纳入 PR CI；每次 PR 都在对应 commit 重新执行并回填本表“当前结果”。
