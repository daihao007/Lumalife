## 1. 站会记录

昨天完成三服务边界、52 个外部 API、内部调用、事件、数据归属和失败处理的 D04 初稿，并通过交叉修订将身份、商家、订单的所有权口径收敛。今天评审该方案是否能在不破坏中期单体演示的前提下进入物理拆分，并建立三个可独立构建、启动、配置和检查健康状态的最小代码入口；同时把验证接入 CI，保留单体回归路径和不可变标签。当前没有阻塞。主要风险是过早复制 `DemoStore`、共享模型或共享数据库，把单体耦合固化到三个进程；因此本次只建立 bootstrap 骨架，不迁移业务、不切换前端路由、不发布伪完整服务。后续按 identity → merchant → order 顺序迁移，每一步以现有契约和 CR-01～CR-06 回归为门禁。

## 2. 评审结论与意见闭环

| 编号 | 评审意见 | 决议 | 闭环证据 |
|---|---|---|---|
| D05-C-01 | 三服务边界采用 identity、merchant、order，网关不拥有业务事实 | 接受 | 入口分别位于 `services/*-service`，没有新增网关业务模块 |
| D05-C-02 | 每个服务应能独立构建和启动 | 接受 | 三个子模块各有 `pom.xml` 和 `*ServiceApplication`；CI 使用三项 matrix 独立执行 `verify` |
| D05-C-03 | 服务必须有独立配置和健康探针 | 接受 | 默认端口 8081/8082/8083；均暴露 health、liveness、readiness、info，并有真实 HTTP 测试 |
| D05-C-04 | 直接复制 `DemoStore`、共享 `Models` 或连接单体 Schema | 拒绝 | 骨架不依赖 `backend`，不包含业务 Entity、Repository 或 datasource |
| D05-C-05 | 本轮直接切换 Compose、前端代理和 K8s 流量 | 延后 | 原单体部署路径保持不变，待业务迁移和全量契约回归后再切流 |
| D05-C-06 | 本轮构建三张可部署业务镜像 | 延后 | 当前服务没有业务 API，提前发布会误报能力；镜像与部署留给后续拆分任务 |
| D05-C-07 | 保持 `/api/v1` 契约、数据独占、无跨库 Join，使用 Outbox/Inbox 与 Saga | 接受为迁移门禁 | 继续以 `docs/19_D04C微服务边界接口与数据归属初稿.md` 和 `docs/contracts/` 为冻结候选 |

结论：方案允许进入“骨架已建立、业务未迁移”阶段。当前三个进程仅证明构建入口、运行配置和平台探针成立，不能描述为三个业务微服务已经完成或可承接生产流量。

## 3. 代码骨架

| 模块 | 启动类 | 默认端口 | 构建入口 |
|---|---|---:|---|
| identity-service | `IdentityServiceApplication` | 8081 | `mvn -B -ntp -f services/identity-service/pom.xml verify` |
| merchant-service | `MerchantServiceApplication` | 8082 | `mvn -B -ntp -f services/merchant-service/pom.xml verify` |
| order-service | `OrderServiceApplication` | 8083 | `mvn -B -ntp -f services/order-service/pom.xml verify` |

聚合入口为 `mvn -B -ntp -f services/pom.xml verify`。端口分别可通过 `LUMALIFE_IDENTITY_PORT`、`LUMALIFE_MERCHANT_PORT`、`LUMALIFE_ORDER_PORT` 覆盖（避开 Kubernetes 注入的同名服务链接变量）。每个模块均提供：

- `/actuator/health`
- `/actuator/health/liveness`
- `/actuator/health/readiness`
- `/actuator/info`

## 4. 单体基线与回滚边界

`monolith-start` 是 annotated tag，标签对象为 `3eb8f44ad2d636eca209c2f119eeae539d2d5136`，解引用提交为 `a1a93529f81ccb3ba1f52b549c8d2027383066e8`。本次未移动、覆盖或重建该标签。

原 `backend/`、`frontend/`、`docker-compose.yml` 和 `k8s/backend.yaml` 的运行流量保持单体路径。若骨架阻断 CI，只需回退 `services/`、新增 CI job 和构建脚本入口；不涉及业务数据回滚。业务迁移前必须继续通过单体 `mvn -B -ntp verify`。

## 6. 后续工作与风险

1. 按 identity → merchant → order 迁移，不允许反向依赖单体 artifact。
2. 先把共享进程内模型转换为版本化 HTTP/事件契约，再迁移数据；不能把 `Models` 复制成事实标准。
3. 三服务建立私有 Schema 前，现有 MySQL 资产仍只属于单体基线。
4. 支付与库存必须以 reservation、幂等键、Outbox/Inbox 和对账任务闭环后才允许切流。
5. 由另一名组员在 PR 上复核独立构建、探针、标签与“不误报业务完成”的文档口径。
