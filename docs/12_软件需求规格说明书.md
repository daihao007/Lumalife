### 1.2 系统概述

LumaLife 面向本地生活课程实践，支持用户发现商家、购物车、外卖与团购下单、支付、履约、评价和客服；支持商家维护经营内容、处理订单、核销券码和回复客服；支持平台管理员查看聚合指标与系统状态。

默认运行链路为：

```text
Browser -> frontend -> backend BFF
                       |-> identity-service -> life_assistant_identity
                       |-> merchant-service -> life_assistant_merchant
                       |-> order-service    -> life_assistant_order
                       `-> assistant-service (无业务数据库)

order-service <-> merchant-service via RabbitMQ Outbox/Inbox/Saga
```

backend 是统一公共入口和 BFF，不计入 4 个业务微服务；系统不存在独立 API Gateway、注册中心或配置中心。Compose 默认运行 8 个服务：frontend、backend、4 个业务微服务、MySQL、RabbitMQ。

## 3 总体需求

### 3.1 用户与角色

| 角色 | 主要能力 | 权限边界 |
| --- | --- | --- |
| 游客 | 浏览分类、商家、详情；使用公共助手 | 不能访问用户、商家或平台管理资源 |
| USER | 资料、地址、收藏、购物车、订单、支付、评价、客服 | 只能访问自己的业务数据 |
| MERCHANT_ADMIN | 商家资料、商品、团购、订单履约、券码、客服 | 只能操作绑定商家数据 |
| PLATFORM_ADMIN | 平台运营指标与系统状态 | 不能代替用户或商家执行交易 |

认证使用 Bearer token。当前 token 为服务端状态映射，不宣称为 JWT；密码使用 BCrypt 编码。真实支付、短信、骑手、地图和生产级个人信息处理不在课程演示范围内。

### 3.2 运行模式

| 模式 | 用途 | 事实状态 |
| --- | --- | --- |
| `prod,remote` | 默认微服务运行；BFF 调用 4 个业务微服务 | 当前交付目标 |
| `monolith` | 单体基线、回滚、局部测试和性能对照 | 保留，不是默认生产链路 |
| 本地前端 | Vite 开发服务器代理 backend | 开发与 UI E2E |

### 3.3 约束

- Java 声明版本 17；前端为 React 18、TypeScript、Vite。
- 金额使用整数分，状态使用枚举，公共响应使用 `{code, message, data}`。
- 三个有状态业务服务各自拥有数据库，禁止跨服务直接 SQL。
- 服务间同步 HTTP 必须配置连接/读取超时；不可用时返回明确 503。
- 库存一致性使用 RabbitMQ、Outbox/Inbox、幂等消费和 Saga 状态，不得描述为同步本地事务。
- AI provider 不可用时返回确定性 fallback；不得虚构通用 circuit breaker 或 retry。

## 4 功能需求

### 4.1 REQ01 账户、资料与地址

系统应支持用户注册、登录、查询当前身份、更新昵称和头像、维护地址及默认地址。公开注册不得选择管理员角色；重复账号、错误密码、越权读取和非法地址操作必须返回明确错误。

验收结果：对应 UC01；identity-service 拥有 `user_account`、`user_address`、`auth_session`。

### 4.2 REQ02 商家发现、详情与收藏

系统应支持分类查询、关键词搜索、价格/评分过滤、推荐或排序、商家详情、商品/团购/评价投影和用户收藏。重复收藏与取消不存在收藏必须可识别。

验收结果：对应 UC02；目录和收藏由 merchant-service 持有。

### 4.3 REQ03 购物车、外卖下单、支付与取消

系统应支持加购、改量、删除、清空、按商家拆单、地址快照、待支付订单、幂等支付与待支付取消。相同 `clientRequestId` 重试不得重复扣库存或产生第二次支付效果；已支付订单不得取消。

验收结果：对应 UC03；订单/支付由 order-service 持有，库存预留由 merchant-service 持有，通过 Saga 协调。

### 4.4 REQ04 履约、收货与评价

商家只能处理自己的订单，并按 `PAID -> ACCEPTED -> DELIVERING -> COMPLETED` 流转；用户随后确认收货并提交一次合法评分。非法跳转、跨商家操作、非法分数和重复评价必须拒绝。

验收结果：对应 UC04；评价真值在 order-service，并投影到 merchant-service 详情。

### 4.5 REQ05 团购购买与券码

用户应能购买有效团购套餐并支付，支付后获得唯一 12 位券码；幂等支付不得生成新券码。数量、库存和团购状态必须校验。

验收结果：对应 UC05。

### 4.6 REQ06 券码核销

绑定商家可核销本店未使用券码；其他商家、未知券码和重复核销必须分别返回越权、不存在或冲突结果。

验收结果：对应 UC06。

### 4.7 REQ07 商家经营维护

商家应能查看和更新资料，维护商品和团购的新增、列表、上下架与删除；所有操作受商家归属约束，发布状态应反映到用户端。

验收结果：对应 UC07。

### 4.8 REQ08 用户、商家与 AI 客服

用户可向指定商家发送消息并获得确定性 AI 回复或 fallback；商家可读取所属会话并人工回复；用户应看到完整往返历史。其他商家不得读取或回复该会话。平台和商家助手均应在 provider 不可用时返回可解释结果。

验收结果：对应 UC08；会话由 merchant-service 持有，生成能力由 assistant-service 提供。

### 4.9 REQ09 平台运营指标

平台管理员应能查看用户、商家、订单、金额、状态和健康聚合；非平台管理员必须拒绝。指标来自 BFF 对各业务服务的聚合，不要求独立报表数据库。

验收结果：对应 UC09。

## 5 外部接口需求

### 5.1 用户接口

前端应提供发现、详情、收藏、购物车、订单、地址、用户客服、商家经营/履约/客服和平台看板页面。关键操作应有加载、成功和错误反馈；角色不可访问的导航不应展示或应被拒绝。

### 5.2 公共 REST 接口

backend 在 8080 端口提供 52 个 `/api/v1/**` 公开业务映射。接口分组如下：

| 分组 | 能力 |
| --- | --- |
| `/auth/**`、`/user/**` | 认证、资料、地址、收藏 |
| `/categories`、`/merchants/**` | 目录、搜索和详情 |
| `/cart/**` | 购物车 |
| `/orders/**`、`/payments`、`/reviews` | 订单、支付、收货和评价 |
| `/conversations/**`、`/assistant/ask` | 用户客服和平台助手 |
| `/merchant-admin/**` | 商家资料、目录、履约、券码、客服和助手 |
| `/admin/metrics` | 平台指标 |

逐接口 method、路径和测试方法见 `docs/testing/public-api-coverage-matrix.md`，当前为 52/52 直接 MockMvc 覆盖。

### 5.3 内部接口

| 服务 | 端口 | 内部业务 API | 数据库 |
| --- | ---: | ---: | --- |
| identity-service | 8081 | 13 | `life_assistant_identity` |
| merchant-service | 8082 | 30 | `life_assistant_merchant` |
| order-service | 8083 | 21 | `life_assistant_order` |
| assistant-service | 8084 | 1 | 无 |

内部接口仅供 BFF 或服务协作使用。调用方必须传递内部身份/服务令牌约定，不得暴露为浏览器公共契约。

### 5.4 通信接口

- 浏览器到 frontend/backend：HTTP。
- BFF 到业务微服务：同步 HTTP，含超时与 503 映射。
- order-service 与 merchant-service：RabbitMQ 事件，使用 durable queue、Outbox/Inbox 和 Saga。
- assistant-service 到可选 provider：HTTPS；无密钥或调用失败时使用本地 fallback。

## 6 数据需求

### 6.1 数据归属

| 服务 | 表数 | 主要数据 |
| --- | ---: | --- |
| identity-service | 3 | 账号、地址、认证会话 |
| merchant-service | 10 | 分类、商家、商品、团购、收藏、会话、库存预留、inbox/outbox |
| order-service | 10 | 购物车、订单、订单行、事件、支付、券码、评价、Saga、inbox/outbox |
| assistant-service | 0 | 无持久化业务表 |

`life_assistant` 仅是 legacy/迁移/回滚源，不是 `prod,remote` 的业务事实源。详细表归属见 `docs/architecture/data-ownership.md`。

### 6.2 一致性与隐私

- 服务只能直接访问自有数据库。
- 跨服务数据通过接口、事件或只读投影传递。
- 密码、token、数据库密码、provider key 不得写入证据和日志。
- 订单金额、库存、券码、支付幂等键和状态转换必须保持可追踪。

## 7 非功能需求

### 7.1 安全

- 角色权限同时在路由和业务归属层校验。
- Secret 通过环境变量或运行时 Secret 注入；仓库不得提交真实凭据。
- 错误响应不得返回密码、token、连接串或内部堆栈。
- 当前尚无完整 secret scanner 证据，状态为 `UNVERIFIED`。

### 7.2 可用性与故障处理

- 所有应用工作负载提供 readiness/liveness/startup probes 和资源 requests/limits。
- 同步依赖不可用时返回显式 503，其他无关服务应继续运行。
- AI 调用使用确定性 fallback。
- 当前实现没有通用 circuit breaker、rate limit、bulkhead 或同步 retry，不得在答辩中声称已实现。

### 7.3 可扩缩与性能

- Kubernetes 为 backend 和 merchant-service 配置 HPA：min 1、max 3、CPU 60%。
- 既有远端证据显示 merchant-service 1 -> 2 -> 3 -> 1，但属于提交 `8c335eb`，不是当前提交重跑。
- 性能对比为 3 API × 2 模式 × 3 次，共 18 runs；既有小样本中单体更快，不得声称微服务性能提升。

### 7.4 可测试性

当前形式化源码测试共 221：Unit/Component 108、Integration/API 94、E2E 19。52 个公开 API 均有直接测试；当前提交的 Microservice E2E 仍为 `NOT-RUN`，旧提交 9/9 只能作为既有证据。
