## 1 范围

### 1.1 标识

本文档适用于 LumaLife 综合生活助手平台。平台是一个前后端分离的本地生活服务演示系统，前端配置项位于 `frontend/`，后端配置项位于 `backend/`，辅助脚本位于 `scripts/`，项目文档位于 `docs/`。

### 1.2 系统概述

LumaLife 面向课程验收场景，提供本地商家发现、商品购买、团购券消费、商家履约和平台运营观测能力。系统覆盖三条业务闭环：

1. **用户消费闭环：** 浏览或搜索商家、查看详情、收藏商家、加入购物车、创建外卖订单、模拟支付、确认收货、评价。
2. **商家履约闭环：** 商家管理员查看本店订单、接单、配送、完成、核销团购券，并维护商品、团购套餐和店铺名称。
3. **平台观测闭环：** 平台管理员查看用户数、商家数、订单数、交易金额、订单分布、营收趋势、商家排行、活跃订单、健康状态和操作日志。

系统当前由 React/Vite 单页前端和 Spring Boot REST 后端组成。后端业务数据主要由 `DemoStore` 维护，使用内存集合运行，并可通过 `lumalife.state-file` 将账号、订单、评价、客服会话、商家资料和收藏等部分状态写入 JSON 文件。Docker Compose 中预留了 MySQL 和 Redis 服务，但本版本业务代码未接入 MySQL/Redis。

## 3 需求

### 3.1 所需的状态和方式

| 状态/方式 | 适用范围 | 行为 |
|---|---|---|
| 正常演示运行 | 全部核心功能 | 后端提供 REST API，前端提供用户、商家和管理员页面，业务数据由 `DemoStore` 处理。 |
| 状态文件恢复 | 后端启动且配置了状态文件 | 读取 JSON 状态，恢复部分账号、订单、评价、会话、商家资料和收藏数据；分类、种子商品等基础数据由代码重新初始化。 |
| AI 降级运行 | 未配置 `AGNES_API_KEY`，或 Agnes API 调用失败 | 客服和商家 AI 助手使用本地规则型兜底回复，不影响浏览、购物车、订单和商家履约功能。 |
| 未认证访问 | 用户尚未登录 | 可浏览分类、商家列表、商家详情，并可调用平台 AI 问答；购物车、订单、地址、收藏和会话等受保护操作不可用。 |

本版本没有实现独立的维护模式、支付超时后台任务、真实支付模式或自动配送模式。任何需求如未特别说明，均适用于正常演示运行状态。

### 3.2 需求概述

#### 3.2.1 目标

平台应为普通用户提供从商家发现到消费评价的连续操作路径，为商家管理员提供订单履约和商品经营工具，为平台管理员提供可观察的运营数据。系统首要目标是稳定演示核心业务规则，而不是实现完整商业化本地生活平台。

系统高层数据流如下：

```mermaid
flowchart LR
    U[普通用户] --> FE[React/Vite 前端]
    M[商家管理员] --> FE
    A[平台管理员] --> FE
    V[游客] --> FE
    FE -->|HTTP JSON /api/v1| API[Spring Boot REST API]
    API --> SEC[Spring Security Token 过滤器]
    SEC --> SVC[业务 Service 门面]
    SVC --> STORE[DemoStore 内存集合]
    STORE --> STATE[(可选 JSON 状态文件)]
    API -.可选.-> AGNES[Agnes AI API]
```

|---|---|
| 后端运行时 | Java 17 及以上，Spring Boot 3.3.5，Maven 3.9 及以上 |
| 前端运行时 | Node.js 18 及以上，npm 9 及以上 |
| 浏览器 | 支持现代 JavaScript、Fetch、Local Storage 和 CSS Grid 的浏览器 |

#### 3.2.3 用户的特点

| 用户 | 特点与目标 |
|---|---|
| 游客 | 不登录即可浏览商家和分类，可能只进行初步发现。 |
| 普通用户 | 具有基本网页操作能力，关注搜索、价格、评分、下单、支付、收货和评价。 |
| 商家管理员 | 负责单个绑定店铺的订单、商品、团购、店铺资料和客服会话，必须理解订单状态和券码核销。 |
| 平台管理员 | 关注平台整体数据、活跃订单、商家排行、健康状态和操作日志。 |

#### 3.2.4 关键点

1. **权限隔离：** 商家管理员只能操作自己绑定商家的订单、商品、团购、评价、券码和客服会话；平台看板仅允许平台管理员访问。
2. **订单状态约束：** 外卖订单必须按 `PENDING_PAYMENT → PAID → ACCEPTED → DELIVERING → COMPLETED` 流转；团购订单按 `PENDING_PAYMENT → PAID → USED` 流转。
3. **支付幂等：** 支付请求必须携带 `clientRequestId`；同一订单以相同请求标识重复支付时返回原订单，不重复扣库存。
4. **库存一致性：** 支付时校验并扣减商品或团购库存，订单通过 `stockDeducted` 标记避免重复扣减。
5. **业务可追踪：** 关键登录、下单、支付、履约、评价、核销和经营操作写入操作日志。
6. **演示可恢复：** 配置状态文件后，部分业务状态可在服务重启后恢复；数据库迁移仍属于后续工作。

#### 3.2.5 约束条件

- 本版本定位为课程演示系统，不处理真实资金，不接入骑手、地图、短信或真实支付网关。
- 当前后端以 `DemoStore` 为核心，未使用 MySQL、Redis 或 MyBatis-Plus 读写业务数据。
- 当前 Token 是随机 UUID 与服务端内存映射，不是 JWT；前端退出登录通过清除浏览器 Local Storage 完成，没有独立登出接口。
- 账号密码只要求非空且长度不少于 6 个字符；代码没有强制 11 位手机号、字母数字组合或登录失败锁定规则。
- 当前购物车可包含多个商家的商品；提交外卖订单时系统按商家拆分为多个订单。
- 前端金额以“分”为后端字段单位，显示时转换为人民币元；商品和套餐价格必须为正数，库存不能为负数。
- 所有图示使用 Mermaid 描述，最终展示效果依赖 Markdown 阅读器对 Mermaid 的支持。

### 3.4 CSCI 能力需求

#### 3.4.1 账户、身份与地址能力

| 编号 | 需求 | 优先级 | 合格性 |
|---|---|---|---|
| AUTH-FR-001 | 系统应允许通过非空账号标识、长度不少于 6 个字符的密码和昵称注册普通用户；账号不能重复，密码应使用 BCrypt 编码后保存。 | P1 | T/I |
| AUTH-FR-002 | 系统应允许演示账号和已注册账号登录；登录成功返回随机 Token 和脱敏用户信息，Token 与角色绑定。错误账号或密码返回未授权错误。 | P1 | T |
| AUTH-FR-003 | 系统应提供当前用户查询、昵称修改和头像 URL 维护；商家管理员修改昵称时，账号昵称和公开店铺名称应同步。 | P2 | T/D |
| AUTH-FR-004 | 普通用户应能新增、编辑、删除和设置默认地址；每个普通用户最多维护 5 个地址；删除默认地址后，系统应为剩余地址自动选择默认地址。 | P1 | T |
| AUTH-FR-005 | 系统应支持通过公开注册入口创建商家管理员及其绑定店铺，但不得通过公开注册入口创建平台管理员。 | P1 | T |

#### 3.5.4 通信接口

- 前端与后端通过 HTTP/JSON 通信，开发环境由 Vite 将 `/api` 和 `/actuator` 代理到 `VITE_API_TARGET`，默认 `http://localhost:8080`。
- 受保护请求使用 `Authorization: Bearer <token>`；前端将 Token 保存在 `localStorage` 的 `lumalife-token` 键中。
- 后端返回整数金额字段，前端使用工具函数转换为人民币元显示。
- 与 Agnes 的可选通信采用 HTTP Chat Completions 风格 JSON，请求带 `Authorization: Bearer <AGNES_API_KEY>`，连接超时和调用失败时使用本地兜底。

### 3.6 CSCI 内部接口需求

当前内部接口边界应保持为：

```text
ApiControllers
  -> AuthService / CatalogService / CartService / OrderWorkflowService
  -> MerchantAdminService / AdminDashboardService / AssistantService / FavoriteService
  -> DemoStore
```

Controller 不应直接维护业务集合或实现订单规则；Service 门面应提供稳定的业务调用边界。后续数据库迁移时，可将 `DemoStore` 替换为 Mapper/Repository 实现，同时保持 `/api/v1/**` 契约不变。

### 3.7 CSCI 内部数据需求

当前主要内部数据集合包括：用户、Token 映射、分类、地址、商家、商品、团购套餐、购物车、订单、券码索引、评价、客服会话、收藏和操作日志。其要求如下：

- User 的密码字段只保存 BCrypt 编码值，安全响应不得返回该字段；
- Order 的金额、商品明细、状态时间线、地址快照、支付请求标识和券码应保持一致；
- Order 状态时间线应记录状态变更时间，用于用户订单展示和管理员配送指标；
- 评价内容保存上限为 200 个字符，客服单条消息保存上限为 500 个字符；
- 状态文件默认为 `./data/lumalife-state.json`，可通过 `lumalife.state-file` 配置；配置为空时测试可关闭状态文件持久化；
- 当前状态文件不持久化购物车、分类、基础商品/套餐全集和实时 Token 映射，重启后这些内容按代码种子和当前内存状态初始化；
- 数据库表、软删除字段、支付记录表和 MySQL 唯一索引属于后续迁移设计，不是当前实现的数据要求。

### 3.9 保密性需求

本项目不存在人身、财产或设备安全控制需求。业务层面的安全要求包括：

- 支付、订单、券码核销和评价操作必须校验订单或资源归属；
- 非法订单状态流转、重复评价、重复核销、库存不足和非法价格/库存输入必须被拒绝；
- 删除商品时清理购物车中的失效项，避免用户继续提交不可购买商品；
- 模拟支付不得宣称产生真实资金结果。

### 3.10 保密性和私密性需求

- 密码必须使用 BCrypt 保存，不出现在 `safeUser` 和管理员账号摘要中；
- 用户只能访问自己的地址、购物车、订单、收藏和会话；
- 商家只能访问绑定店铺的数据；
- 评价展示使用昵称脱敏规则；
- `.env`、AI 密钥及本地状态文件不应提交到版本库；
- 当前版本使用演示账号和演示数据，不得用于真实支付或生产个人信息处理。

### 3.15 数据

#### 3.15.1 输入数据

账号、密码、昵称、头像 URL、地址、搜索关键词、分类和排序参数、商品数量、地址 ID、团购 ID、支付订单 ID、客户端支付请求 ID、状态转移目标、券码、评分、评价文字、客服消息和商家维护信息。

#### 3.15.2 输出数据

商家分页列表、商家详情、购物车明细、订单及状态时间线、支付结果、券码、评价、客服消息、商家后台资源、管理员指标和统一错误响应。

#### 3.15.3 数据约束

- 价格用 `long` 表示分；库存用非负整数；评分范围为 1 至 5；
- 页面列表默认请求 20 条，服务端返回 `records/page/size/total/pages`；
- 订单总额等于订单明细单价乘以数量之和；
- 支付成功才扣减库存并改变订单状态；
- 评价必须关联本人订单且一单一评。

### 3.17 故障处理

| 场景 | 当前处理 |
|---|---|
| 参数错误 | 返回业务错误码 `40000`，HTTP 400。 |
| 未认证 | Spring Security 返回 HTTP 401。 |
| 角色不匹配 | Spring Security 返回 HTTP 403。 |
| 资源不存在 | 返回业务错误码 `40400`，HTTP 404。 |
| 业务冲突 | 返回 `40900` 或其他非 400/401/403/404 业务码，HTTP 409。 |
| 服务器异常 | 全局异常处理器返回 HTTP 500 和 `50000`。 |
| AI 服务不可用 | 记录日志并返回本地规则型回复。 |
| 下架、缺货、非法流转 | 拒绝操作并返回中文业务提示，不改变原有有效状态。 |

成功和业务异常通常使用 `{code, message, data}`；认证过滤器产生的 401/403 响应由 Spring Security 处理，前端应将其视为登录失效或无权访问。

### 3.18 算法说明

#### 3.18.1 默认推荐算法

没有用户历史时，商家综合质量分为：

```text
qualityScore = 0.6 × (avgScore / 5.0)
             + 0.4 × max(0, 1 - distanceKm / 5.0)
```

有用户历史且排序方式为 `recommend` 时，系统综合以下信号：品类偏好、用户平均消费匹配度、商家质量、复购/高评价行为和销量热度。实现中的加权形式为：

```text
recommendScore = 0.25 × categoryScore
               + 0.20 × priceScore
               + 0.20 × qualityScore
               + 0.25 × behaviorScore
               + 0.10 × popularityScore
```

无历史时退化为 `qualityScore`。推荐结果同时返回面向用户的推荐理由。

#### 3.18.2 订单状态规则

```text
外卖：PENDING_PAYMENT → PAID → ACCEPTED → DELIVERING → COMPLETED
                                  └→ 用户确认收货：RECEIVED
取消：PENDING_PAYMENT → CANCELLED
团购：PENDING_PAYMENT → PAID → USED
```

当前商家接口只允许外卖订单按相邻状态流转；团购订单通过券码核销从 `PAID` 变为 `USED`。代码中定义了 `EXPIRED`，但当前没有自动过期任务。

#### 3.18.3 支付和库存规则

支付前校验订单归属、待支付状态和 `clientRequestId`；首次支付调用库存扣减逻辑，成功后设置 `stockDeducted=true`，再变更为 `PAID`。重复请求若使用相同客户端请求标识直接返回原订单。

#### 3.18.4 券码规则

团购订单支付成功后根据订单 ID 生成 12 位数字券码，并写入券码索引。商家核销时校验券码存在、订单属于当前商家且状态为 `PAID`。

## 6 尚未解决的问题

1. **数据库持久化：** 当前 MySQL 和 Redis 只是 Docker Compose 预留，业务仍由内存集合和可选 JSON 状态文件处理；后续应按 `docs/11_数据库持久化迁移计划.md` 逐个 Service 迁移。
2. **Token 生命周期：** 当前 Token 是服务端内存 UUID 映射，没有过期时间、刷新、撤销和独立登出接口；浏览器退出只清除本地 Token。
3. **购物车持久化：** 当前购物车没有写入状态文件，后端重启后可能丢失。
4. **支付记录：** 当前没有独立支付记录实体，支付信息主要保存在订单的 `clientRequestId`、状态和时间线中。
5. **自动任务：** `EXPIRED` 状态已定义，但没有团购券自动过期和待支付订单超时取消任务。
6. **并发控制：** 当前集合使用主要用于课程演示，未实现数据库事务、分布式锁或高并发库存控制。
7. **接口一致性：** 统一业务错误响应由全局异常处理器提供，但 Spring Security 直接产生的 401/403 可能没有完整 JSON 响应体，前端错误解析仍可进一步统一。
8. **推荐输入：** 当前距离和基础商家统计为演示数据，不接收真实定位，不提供地图或动态配送时间。
9. **AI 安全边界：** 平台 AI 接口当前公开；若接入真实业务上下文，应增加鉴权、限流、内容安全和隐私评估。
10. **文档同步：** 旧文档中存在“23 个测试”“JWT”“MySQL 已接入”等与当前代码不一致的描述，后续发布文档应以本 SRS 和实际代码为准。

## 7 注解

### 7.1 术语说明

- **CSCI：** Computer Software Configuration Item，计算机软件配置项，本文指 LumaLife 平台整体。
- **SRS：** Software Requirements Specification，软件需求规格说明书。
- **REST API：** 通过 HTTP 方法和资源路径提供服务的接口形式。
- **Token：** 登录成功后返回的随机访问令牌；当前实现为服务端内存映射的 UUID，不是 JWT。
- **DemoStore：** 当前演示版的核心状态和业务规则存储类。
- **幂等性：** 同一请求重复执行不会造成额外业务副作用；本项目主要用于支付请求。
- **状态时间线：** 订单各状态及其发生时间的有序记录。
- **券码核销：** 商家确认已支付团购券可用，并将订单从 `PAID` 变为 `USED`。
- **Bearer Token：** 放在 HTTP `Authorization` 请求头中的令牌格式。
- **Agnes API：** 可选的外部 AI 对话接口；不可用时使用本地规则回复。

#### UC-01 账号注册与登录

**用户故事：** 作为游客，我希望注册或登录账号，以便获得与角色匹配的功能入口。

**参与者：** 游客、普通用户、商家管理员。  
**前置条件：** 游客能够访问登录页面；注册账号标识尚未被使用。  
**触发条件：** 用户提交注册表单或登录表单。

**基本流程：**

1. 用户选择普通用户或商家管理员注册，输入账号、密码和昵称。
2. 系统校验账号非空、密码长度和账号唯一性；商家注册时创建并绑定新店铺。
3. 系统对密码进行 BCrypt 编码，保存账号并返回登录结果。
4. 已有用户输入账号和密码，系统验证凭据。
5. 登录成功后系统生成随机 Token，前端保存 Token 并按角色进入发现页、商家订单页或平台看板。

**异常与后置条件：** 重复账号、密码过短或凭据错误时返回明确错误；平台管理员不能通过公开注册创建。成功后形成登录会话。

```mermaid
sequenceDiagram
    actor Visitor as 游客/用户
    participant System as LumaLife 系统
    Visitor->>System: 提交注册或登录信息
    alt 注册
        System->>System: 校验账号、密码和角色
        alt 商家注册
            System->>System: 创建商家并绑定账号
        end
        System->>System: BCrypt 编码密码并保存
        System-->>Visitor: 返回 Token 和用户信息
    else 登录
        System->>System: 查询账号并校验密码
        System-->>Visitor: 返回 Token 和角色信息
    end
```

#### UC-07 外卖支付与取消

**用户故事：** 作为普通用户，我希望对待支付订单进行模拟支付或取消，以便控制订单是否进入商家履约。

**参与者：** 普通用户。  
**前置条件：** 订单属于当前用户；支付订单必须为 `PENDING_PAYMENT`。  
**基本流程：** 用户提交订单 ID 和 `clientRequestId`；系统校验幂等标识，扣减一次库存并变为 `PAID`；或对待支付订单执行取消。

**异常与后置条件：** 请求标识为空、订单不属于用户、订单状态不允许支付/取消时拒绝；重复支付返回原订单，不重复扣库存。

```mermaid
stateDiagram-v2
    [*] --> PENDING_PAYMENT: 创建外卖订单
    PENDING_PAYMENT --> PAID: 首次模拟支付
    PENDING_PAYMENT --> CANCELLED: 用户取消
    PAID --> PAID: 相同 clientRequestId 重复支付
    PAID --> [*]
    CANCELLED --> [*]
```

#### UC-08 外卖履约与确认收货

**用户故事：** 作为商家管理员，我希望按顺序处理本店订单；作为用户，我希望在配送后确认收货，以便完成履约闭环。

**参与者：** 商家管理员、普通用户。  
**前置条件：** 外卖订单已支付；商家管理员与订单商家匹配。  
**基本流程：** 商家依次将订单从 `PAID` 改为 `ACCEPTED`、`DELIVERING`、`COMPLETED`；用户在配送中或完成状态下确认收货，订单变为 `RECEIVED`。

**异常与后置条件：** 跳过状态、处理他店订单、处理团购订单或未配送确认收货时拒绝；每次状态变更写入时间线和操作日志。

```mermaid
stateDiagram-v2
    [*] --> PAID: 用户支付
    PAID --> ACCEPTED: 商家接单
    ACCEPTED --> DELIVERING: 开始配送
    DELIVERING --> COMPLETED: 商家完成
    DELIVERING --> RECEIVED: 用户确认收货
    COMPLETED --> RECEIVED: 用户确认收货
    PAID --> [*]: 非法跳转
```

#### UC-09 团购购买与券码

**用户故事：** 作为普通用户，我希望购买有效团购套餐并获得券码，以便到店使用。

**参与者：** 普通用户。  
**前置条件：** 套餐存在、启用且库存满足购买数量。  
**基本流程：** 用户在商家详情选择套餐，系统创建待支付团购订单；用户模拟支付后，系统扣减套餐库存、生成 12 位数字券码并返回。

**异常与后置条件：** 套餐停用、套餐不存在、库存不足或支付失败时不生成可用券码；成功后订单状态为 `PAID`。

```mermaid
sequenceDiagram
    actor User as 普通用户
    participant System as LumaLife 系统
    User->>System: 提交团购套餐 ID 和数量
    System->>System: 校验套餐启用状态和库存
    System-->>User: 返回待支付团购订单
    User->>System: 提交订单支付请求
    System->>System: 幂等校验并扣减套餐库存
    System->>System: 生成 12 位数字券码
    System-->>User: 返回已支付订单和券码
```

#### UC-10 团购券核销

**用户故事：** 作为商家管理员，我希望核销本店有效团购券，以便确认用户已到店消费。

**参与者：** 商家管理员。  
**前置条件：** 商家管理员已登录；券码对应订单存在且已支付。  
**基本流程：** 商家输入券码，系统查询券码索引、校验商家归属和订单状态，将订单置为 `USED` 并记录日志。

**异常与后置条件：** 券码不存在、属于其他商家或已核销时拒绝；核销成功后不可再次核销。

```mermaid
sequenceDiagram
    actor Merchant as 商家管理员
    participant System as LumaLife 系统
    Merchant->>System: 提交团购券码
    System->>System: 查询券码和订单
    System->>System: 校验商家归属及 PAID 状态
    alt 校验通过
        System->>System: 将订单变为 USED 并写日志
        System-->>Merchant: 返回核销成功
    else 校验失败
        System-->>Merchant: 返回不存在、越权或重复核销提示
    end
```

#### UC-11 评价与评分

**用户故事：** 作为普通用户，我希望评价已完成的订单，以便记录体验并帮助其他用户判断商家。

**参与者：** 普通用户、商家管理员。  
**前置条件：** 订单属于当前用户，状态为 `RECEIVED`、`COMPLETED` 或 `USED`，且尚未评价。  
**基本流程：** 用户提交总评分、口味评分、服务评分和文字；系统校验范围和内容，创建脱敏用户评价并标记订单已评价；商家可查看本店评价。

**异常与后置条件：** 未完成订单、重复评价、评分不在 1 至 5 或空内容时拒绝；评价影响商家实时评分展示。

```mermaid
sequenceDiagram
    actor User as 普通用户
    participant System as LumaLife 系统
    User->>System: 提交订单评价和三项评分
    System->>System: 校验订单归属、状态、一单一评和评分范围
    alt 校验通过
        System->>System: 脱敏昵称并保存评价
        System->>System: 标记订单 reviewed=true
        System-->>User: 返回评价结果
    else 校验失败
        System-->>User: 返回评价错误
    end
```

#### UC-12 商家经营维护

**用户故事：** 作为商家管理员，我希望维护商品、团购套餐和店铺名称，以便公开页面展示准确的经营信息。

**参与者：** 商家管理员。  
**前置条件：** 商家管理员已登录并绑定有效店铺。  
**基本流程：** 商家新增或编辑商品/套餐，修改价格、库存、上架或启用状态；也可删除本店资源和修改店铺展示名称。系统校验资源归属并返回最新数据。

**异常与后置条件：** 价格不合法、库存为负、资源不属于当前商家或资源不存在时拒绝；删除商品清理购物车项，店铺名称同步公开列表和订单显示。

```mermaid
flowchart TD
    A([商家进入管理页]) --> B{选择维护对象}
    B -->|商品| C[新增/编辑/上下架/删除商品]
    B -->|团购| D[新增/编辑/启用/停用/删除套餐]
    B -->|店铺| E[修改店铺名称]
    C --> F[校验 merchantId、价格和库存]
    D --> F
    E --> G[校验名称并同步账号与店铺]
    F --> H{校验通过?}
    H -->|是| I[保存并写操作日志]
    H -->|否| J[返回业务错误]
    G --> I
    I --> K([结束])
    J --> K
```

#### UC-13 客服会话与 AI 辅助

**用户故事：** 作为用户，我希望向平台或商家咨询；作为商家，我希望查看会话、人工回复并使用 AI 辅助生成回复。

**参与者：** 普通用户、商家管理员、Agnes AI（可选）。  
**前置条件：** 商家会话要求用户登录；商家侧要求商家管理员登录；平台 AI 问答当前可公开调用。  
**基本流程：** 用户发送不超过 500 字消息，系统保存消息并调用本地规则或 Agnes 生成回复；商家查看本店会话并可人工回复或请求 AI 建议。

**异常与后置条件：** 空消息被拒绝；远程 AI 超时、密钥为空或返回异常时使用本地兜底；会话数据在状态文件配置有效时可恢复。

```mermaid
sequenceDiagram
    actor User as 用户
    actor Merchant as 商家管理员
    participant System as LumaLife 系统
    participant Agnes as Agnes API
    User->>System: 发送平台问题或商家消息
    System->>System: 校验内容长度并保存用户消息
    alt 商家会话
        System->>Agnes: 可选：提交店铺上下文和历史消息
        Agnes-->>System: 返回建议回复
        System-->>User: 返回 AI/兜底回复并保存会话
        Merchant->>System: 查询会话并发送人工回复
        System-->>User: 返回商家回复
    else 平台问答
        System->>Agnes: 可选：提交平台问题
        Agnes-->>System: 返回回答
        System-->>User: 返回 AI/规则回答
    end
```

#### UC-14 平台看板

**参与者：** 平台管理员。  
**前置条件：** 管理员已使用 `PLATFORM_ADMIN` 账号登录。  
**基本流程：** 管理员打开看板，系统聚合用户、商家、订单、金额、趋势、排行、配送时效、活跃订单、健康状态、账号和日志并返回；前端使用图表和表格展示。

**异常与后置条件：** 非平台管理员访问返回 403；看板只读，不改变交易数据。

```mermaid
sequenceDiagram
    actor Admin as 平台管理员
    participant System as LumaLife 系统
    Admin->>System: 请求平台指标
    System->>System: 校验 PLATFORM_ADMIN 角色
    System->>System: 聚合订单、金额、趋势、排行、健康和日志
    System-->>Admin: 返回看板数据
    Admin->>System: 刷新或查看账号/活跃订单
    System-->>Admin: 返回当前只读指标
```
