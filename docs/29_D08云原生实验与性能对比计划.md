## 2. HPA 实验

生产清单对 backend 和 merchant-service 设置 CPU request、`minReplicas=1`、`maxReplicas=3` 和 60% CPU 目标；扩容立即生效，缩容有 120 秒稳定窗口，避免短时抖动。目标集群需要提供 Resource Metrics API（通常由 metrics-server 提供），否则 HPA 只能创建但不能根据 CPU 调整副本数。本轮实验优先 merchant-service。

```bash
kubectl -n lumalife get hpa merchant-service
NAMESPACE=lumalife LOAD_SECONDS=180 COOLDOWN_SECONDS=180 \
  bash 04_tests/cloud-native/run-hpa-experiment.sh
```

脚本输出副本、HPA 当前/期望值、CPU/内存、吞吐、平均延迟、P95 和错误数；原始 CSV、负载日志、`kubectl top` 日志及 HPA 清单要随报告提交。若 `metrics.k8s.io` 不可用，相关字段保留为 `N/A`，不得把实验写成成功扩容。

## 3. 故障处理实验

微服务之间只通过 HTTP 调用；BFF 对远程服务连接/读取失败映射为明确的 503 业务错误，不让异常堆栈泄漏给用户。实验步骤：

```bash
kubectl -n lumalife scale deployment/merchant-service --replicas=0
curl -i 'http://localhost:30080/api/v1/merchants?keyword=%E5%92%96%E5%95%A1'
kubectl -n lumalife get pods
kubectl -n lumalife scale deployment/merchant-service --replicas=1
```

应记录：商家查询得到预期不可用提示；identity/order/数据库等未被级联停止；恢复依赖服务后健康检查和查询恢复。线上演示使用隔离窗口或验收集群，不直接对无窗口生产流量注入故障。本轮实测证据见 `04_tests/cloud-native/fault/summary.md` 和 `docs/FAULT_TOLERANCE_EXPERIMENT_REPORT.md`。

## 4. 性能对比

正式实验必须固定：同一机器、同一批种子数据、同一个公开接口、同一并发和请求数。先以微服务开关全开运行，再以显式 `monolith` profile 运行单体兼容路径。`run-comparison.sh` 对商家搜索、分类列表、商家详情使用同一个 `load-test.mjs`，每边每个 API 运行 3 次，并保存吞吐量、平均耗时、P95、错误率和 backend Docker CPU/内存。

性能结果只能引用实际生成的 artifact/CSV。报告需要解释远程 HTTP、数据库访问和服务启动成本造成的差异，不能仅凭理论声称“微服务更快”。本轮实际结果见 `04_tests/performance/results/nightly-20260902/comparison-summary.csv`。
