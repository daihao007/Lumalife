## 2. HPA 实验

生产清单对 backend 设置 CPU request、`minReplicas=1`、`maxReplicas=3` 和 60% CPU 目标；扩容立即生效，缩容有 120 秒稳定窗口，避免短时抖动。目标集群需要提供 Resource Metrics API（通常由 metrics-server 提供），否则 HPA 只能创建但不能根据 CPU 调整副本数。

```bash
kubectl -n lumalife get hpa backend
NAMESPACE=lumalife LOAD_SECONDS=180 COOLDOWN_SECONDS=180 \
  bash 04_tests/cloud-native/run-hpa-experiment.sh
```

脚本输出 `phase,timestamp,pods,ready_pods,hpa_current,hpa_desired,cpu_target`，原始 CSV 要随报告提交。演示时至少展示 baseline、load 中 `desiredReplicas > 1` 和 cooldown 回到 1 的记录。

## 3. 故障处理实验

微服务之间只通过 HTTP 调用；BFF 对远程服务连接/读取失败映射为明确的 503 业务错误，不让异常堆栈泄漏给用户。实验步骤：

```bash
kubectl -n lumalife scale deployment/merchant-service --replicas=0
curl -i 'http://localhost:30080/api/v1/merchants?keyword=%E5%92%96%E5%95%A1'
kubectl -n lumalife get pods
kubectl -n lumalife scale deployment/merchant-service --replicas=1
```

应记录：商家查询得到预期不可用提示；identity/order/数据库等未被级联停止；恢复依赖服务后健康检查和查询恢复。线上演示使用隔离窗口或验收集群，不直接对无窗口生产流量注入故障。

## 4. 性能对比

正式实验必须固定：同一机器、同一批种子数据、同一个公开接口、同一并发和请求数。先以微服务开关全开运行，再以三个 `LUMALIFE_*_REMOTE_ENABLED=false` 运行单体兼容路径。脚本默认每边 3 次，输出吞吐量、平均耗时、P95、错误率；CPU 和内存由实验环境另行记录。

性能结果只能引用实际生成的 artifact/CSV。报告需要解释远程 HTTP、数据库访问和服务启动成本造成的差异，不能仅凭理论声称“微服务更快”。
