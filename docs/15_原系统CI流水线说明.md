# 原系统 CI 构建、测试和镜像流水线

## 1. 目标

本流水线对应看板任务 `[D04][E][2026-08-28] 建立原系统 CI 构建、测试和镜像流水线`，覆盖原有单体系统的持续集成：

1. 编译并测试 Spring Boot 后端；
2. 安装依赖并构建 Vue 前端；
3. 只有前两项全部成功，才构建前后端 Docker 镜像；
4. 合并或推送到 `main` 后，将带版本标识的镜像发布到 GitHub Container Registry（GHCR）。

Kubernetes 自动部署、健康检查和回滚由 Issue #40 的后续流水线阶段负责，详见 `docs/19_D05_Kubernetes自动部署与健康检查.md`。

## 2. 触发方式

流水线文件：`.github/workflows/ci.yml`

| 触发事件 | 测试与构建 | Docker 镜像构建 | 发布到 GHCR |
| --- | --- | --- | --- |
| 向 `main` 提交 PR | 是 | 是 | 否 |
| 推送到 `main` | 是 | 是 | 是 |
| 在 `main` 手动运行 | 是 | 是 | 是 |

PR 阶段只验证镜像能够成功构建，不发布镜像，避免未评审代码进入镜像仓库。

## 3. 流水线门禁

```text
后端编译与测试 ─┐
                ├─> 质量门禁 ─> 后端镜像构建/发布
前端依赖与构建 ─┘             └> 前端镜像构建/发布
```

`images` 作业依赖 `quality-gate`，而质量门禁又依赖后端、前端、数据库、Compose、E2E 和 Kubernetes 清单检查。后续 Kubernetes 冒烟与真实部署继续依赖 `images`。因此任一前序步骤失败，镜像发布和部署都会被 GitHub Actions 自动跳过。

## 4. 镜像及版本标签

镜像地址：

- `ghcr.io/daihao007/lumalife-backend`
- `ghcr.io/daihao007/lumalife-frontend`

推送到 `main` 时生成两类标签：

- `sha-<短提交号>`：精确对应一次 Git 提交，用于追溯和回滚；
- `main`：指向 `main` 分支最近一次通过流水线的镜像。

流水线不使用无法精确追溯的 `latest` 作为唯一标签。

## 5. 验收与证据留存

### 成功流水线

1. 打开仓库的 **Actions → Monolith CI**；
2. 选择一次 `main` 分支的成功运行；
3. 确认 `Backend test`、`Frontend build`、`Quality gate` 和两个镜像作业均成功；
4. 在仓库 **Packages** 中确认前后端镜像均存在 `sha-*` 和 `main` 标签；
5. 将运行链接和镜像标签记录到对应 Issue。

### 失败门禁演示

1. 打开 **Actions → Monolith CI → Run workflow**；
2. 勾选 `demonstrate_failure_gate` 后运行；
3. `Quality gate` 会按预期失败；
4. 确认两个 `Build ... image`、`Kubernetes rollout smoke test` 和 `Deploy Kubernetes` 作业均为 `Skipped`，证明失败不会发布镜像或部署；
5. 将该失败运行链接记录到对应 Issue。

该开关只用于生成课程要求的失败门禁证据，不影响正常 PR 和 `main` 分支流水线。

## 6. 权限与维护

- 默认权限仅为 `contents: read`；
- 只有镜像作业获得 `packages: write`；
- 使用 GitHub 自动提供的 `GITHUB_TOKEN` 登录 GHCR，不在仓库中保存账号密码；
- 相同分支有新提交时，会取消尚未结束的旧运行，减少重复资源消耗。
