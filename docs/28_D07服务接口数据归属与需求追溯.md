## 1. 验收结论和口径

Issue #46 的验收需要同时回答四个问题：服务实际暴露了什么接口、每类数据现在由谁写入、REQ/UC 如何落到代码和测试、当前实现与拆分目标还有什么差异。

本次核对结论如下：

1. `identity-service`、`merchant-service`、`order-service` 已是三个可独立启动的 Spring Boot 进程，实际内部业务接口分别为 9、12、18 个，合计 39 个；每个服务另有 health/liveness/readiness/info 探针。
2. 浏览器仍只访问 backend 的 `/api/v1/**` 兼容入口；`/internal/v1/**` 是集群内服务接口，不是前端接口。契约文档中按服务归属统计的 52 个外部目标接口，与当前已实现的 39 个内部接口不是同一组数量。
3. 当前生产运行时仍使用一个 MySQL 数据库 `life_assistant`。`merchant_catalog`、`order_record` 及 `service_*` 表是逻辑上的服务表，不是独立物理 Schema；identity 当前使用可选 JSON 状态文件，不使用 MySQL。
4. Kubernetes 清单打开了三类远程路由，但 merchant 的分类/收藏/客服/AI 等能力仍回到 `DemoStore`，而 order 与 merchant 的跨服务库存预占、Outbox/Inbox、事件总线和 Saga 仍是目标设计，不得写成已完成。

因此，本文是 D07 的当前事实索引；目标字段、未来错误外壳和事件载荷仍以 [`docs/16_三服务接口数据归属与契约草案.md`](./16_三服务接口数据归属与契约草案.md) 与 [`docs/contracts/`](./contracts/) 为准，若二者冲突，以源码、测试和本文件的“当前实现”列为准。

## 4. 数据归属：当前实现和目标设计

### 4.1 当前写入事实

| 逻辑所有者 | 当前实际写入/读取 | 当前状态 | 不能误写成 |
|---|---|---|---|
| identity-service | `IdentityStore` 的用户、token、地址 map；可选 `identity-state.json` | 服务代码有重启持久化测试，但不是 MySQL；Kubernetes 清单通过 `identity-data` PVC 挂载 JSON 文件，仍需验证 ECS 运行时回收/恢复策略 | 独立 identity Schema 或 JWT 会话库已完成 |
| merchant-service | `merchant`、`category` 读取；商品通过 `merchant_catalog` CRUD；团购在 JDBC 可用时通过 `group_deal` CRUD，否则使用 `deals` map | 商品和团购已有关系表路径；只有未配置 JDBC 的 fallback 才是内存路径，生产部署需确认 JDBC 配置 | merchant 全部事实已完成独立数据库化 |
| order-service | `order_record`、`service_order_line`；购物车 `service_cart_item`；支付 `service_payment`；券码 `service_coupon`；评价 `service_review`；状态事件 `service_order_event` | MySQL 模式下具备主要关系落点、订单详情和支付幂等唯一键；外卖订单支持保存多条明细，但仍未完成库存 Saga/事件基础设施 | 完整订单快照、库存 Saga、Outbox/Inbox 已完成 |
| backend/DemoStore | 未迁移能力的单体兼容数据，包括部分分类、收藏、客服/AI、指标和 fallback | 作为渐进迁移的回退路径存在；远程调用失败时 identity token 查询也会回退 | 网关已经没有业务数据 |

### 4.2 数据库迁移文件与归属

| 迁移 | 当前资产 | 归属说明 |
|---|---|---|
| `V001` | 单体基础表：`user_account`、`user_address`、`merchant`、`category`、`product`、`group_deal`、`cart_item`、`order_main`、`order_item`、`payment_record` 等 | 历史兼容/单体事实，不能由新服务直接跨域写入 |
| `V003` | `business_state` | 旧单体 JSON 快照兼容表；不是服务事件表 |
| `V004` | `merchant_catalog`、`order_record` | 渐进迁移的 merchant/order 逻辑服务表，共享同一 MySQL 物理库 |
| `V005` | `service_cart_item`、`service_payment`、`service_coupon`、`service_review` | order-service 逻辑所有者；无跨服务外键 |
| `V006` | order 类型、支付请求键、券码/地址/版本字段和 `service_order_event` | 为 order 服务状态和幂等补充的增量结构 |
| `V007` | `service_payment(user_id, client_request_id)` 唯一键 | 将支付幂等范围扩展为同一用户全局唯一 |
| `V008` | `service_order_line(order_id, line_no, item_id, item_name, quantity, price_cent)` | 为 order-service 保存多商品订单明细快照；仍与历史单体 `order_item` 表区分 |

当前约束是“同库逻辑隔离”：服务代码必须通过自己的 Repository/Store 访问自己的表，不能因为物理上同库就跨域 Join 或建立第二个可写入口。

## 6. 单体差异与未完成项

| 差异项 | 当前实现 | 目标设计 | D07 结论/后续门禁 |
|---|---|---|---|
| 外部入口 | backend 仍承接全部 `/api/v1/**` | 网关兼容，内部服务拥有事实 | 当前合理；必须保留 BFF → service → store 追溯 |
| 物理数据库 | 一个 `life_assistant` MySQL，逻辑服务表并存 | identity/merchant/order 独立 Schema 或数据库 | 未完成；需要迁移、回填和重启证据 |
| identity 持久化 | JSON 文件/内存，非 JDBC；Kubernetes 通过 `identity-data` PVC 挂载 `/app/data` | 身份库、会话库和可轮换 token | 未完成；当前不是 JWT，PVC 只解决文件持久化载体，不等于独立 identity 数据库 |
| merchant 团购 | JDBC 可用时读写 `group_deal`，否则使用 `MerchantStore.deals` 内存 map | merchant 持久化套餐、库存和版本 | 关系表路径已具备；仍需生产配置、重启和并发库存证据 |
