## 1. 验收结论和口径

Issue #46 的验收需要同时回答四个问题：服务实际暴露了什么接口、每类数据现在由谁写入、REQ/UC 如何落到代码和测试、当前实现与拆分目标还有什么差异。

本次核对结论如下：

1. `identity-service`、`merchant-service`、`order-service`、`assistant-service` 已是四个可独立启动的 Spring Boot 进程，前三者承载业务数据，assistant 承载 AI provider；每个服务另有 health/liveness/readiness/info 探针。
2. 浏览器仍只访问 backend 的 `/api/v1/**` 兼容入口；`/internal/v1/**` 是集群内服务接口，不是前端接口。契约文档中按服务归属统计的 52 个外部目标接口，与当前已实现的 39 个内部接口不是同一组数量。
3. 默认生产运行时保留同一 MySQL 实例上的四个数据库以兼容旧数据；`docker-compose.physical-db.yml` 已提供三个服务库独立 MySQL 实例和按表导出迁移路径。旧库仍保留用于兼容/回滚，不能再视为服务的可写事实源。
4. Kubernetes 清单打开了四类远程路由，assistant 已独立部署；`DemoStore` 受 `monolith` profile 限制，生产远程 profile 不会静默加载。订单和 merchant Outbox 已接入 RabbitMQ，双方 Inbox 负责幂等消费，`order_inventory_saga` 记录确认/释放结果；库存预占仍保留同步兼容窗口，不能写成支付入口完全异步化。

因此，本文是 D07 的当前事实索引；目标字段、未来错误外壳和事件载荷仍以 [`docs/16_三服务接口数据归属与契约草案.md`](./16_三服务接口数据归属与契约草案.md) 与 [`docs/contracts/`](./contracts/) 为准，若二者冲突，以源码、测试和本文件的“当前实现”列为准。

## 4. 数据归属：当前实现和目标设计

### 4.1 当前写入事实

| 逻辑所有者 | 当前实际写入/读取 | 当前状态 | 不能误写成 |
|---|---|---|---|
| identity-service | `life_assistant_identity` 中的用户、token、地址表；无 JDBC 时仍可使用 JSON/内存测试路径 | 服务库已从兼容库回填，生产 JDBC 不再依赖旧库；JSON 仅是无数据库 smoke/fallback 载体 | JWT/会话轮换、跨服务身份事件仍未完成 |
| merchant-service | `life_assistant_merchant` 中的 `merchant`、`category`、`merchant_catalog`、`group_deal`、收藏、客服和库存事件表 | 商品/商家主写入已进入服务库，部署前执行幂等回填；未启用 JDBC 的 smoke 路径仍使用内存 | 商家事实的独立数据库化已完成；预占命令仍保留 HTTP 兼容入口 |
| order-service | `life_assistant_order` 中的 `order_record`、`service_order_line`、购物车、支付、券码、评价、状态事件、Outbox、Inbox 和 Saga 表 | 服务库已从兼容库回填；MySQL 模式下具备订单详情、支付幂等、事务 Outbox、RabbitMQ 发布和结果幂等消费 | 库存预占仍是同步 HTTP 兼容命令；确认和反向释放已走事件链路 |
| assistant-service | 无业务表；接收 BFF 的请求级上下文并调用 Agnes，缺少 key 时在本服务内降级 | AI provider 与降级逻辑独立部署，商家会话由 merchant-service 持久化 | 不应再把 AI provider 描述成 backend 的默认生产能力 |
| backend/DemoStore | 仅在 `monolith` profile 且 `LUMALIFE_COMPATIBILITY_STORE_ENABLED=true` 时提供单体兼容数据和回退端口 | 作为显式渐进迁移回退路径保留；远程生产 profile 不会创建该 Bean | 远程模式不会静默回到 DemoStore；单体 profile 仍可回滚 |

### 4.2 数据库迁移文件与归属

| 迁移 | 当前资产 | 归属说明 |
|---|---|---|
| `V001` | 单体基础表：`user_account`、`user_address`、`merchant`、`category`、`product`、`group_deal`、`cart_item`、`order_main`、`order_item`、`payment_record` 等 | 历史兼容/单体事实，不能由新服务直接跨域写入 |
| `V003` | `business_state` | 旧单体 JSON 快照兼容表；不是服务事件表 |
| `V004` | `merchant_catalog`、`order_record` | 渐进迁移的 merchant/order 逻辑服务表，共享同一 MySQL 物理库 |
| `V005` | `service_cart_item`、`service_payment`、`service_coupon`、`service_review` | order-service 逻辑所有者；无跨服务外键 |
| `V006` | order 类型、支付请求键、券码/地址/版本字段和 `service_order_event` | 为 order 服务状态和幂等补充的增量结构 |
| `V007` | `service_payment(user_id, client_request_id)` 唯一键 | 将支付幂等范围扩展为同一用户全局唯一 |
| `V008` | `service_order_line(order_id, line_no, item_id, item_name, quantity, price_cent)` | 为 order-service 保存多商品订单明细快照；仍与历史单体 `order_item` 表区分 |

当前约束是“服务库物理隔离”：服务代码必须通过自己的 Repository/Store 访问自己的数据库，不能跨库 Join、跨域写表或建立第二个可写入口；`life_assistant` 只作为渐进迁移兼容源。
